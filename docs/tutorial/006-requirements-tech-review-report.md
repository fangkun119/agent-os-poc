## 2. 评审方法：把 63 轮问答变成四类产出物

### 2.1 评审不是找 bug，是收口

你可能会问：技术评审不就是找人帮忙挑代码毛病吗？这份报告的总体结论里有一条很反直觉的判断——"浮出的问题是留白，不是设计错误"。63 轮问答里几乎没有发现逻辑错误，真正的问题是另一类：设计者想到了、但没写下来的参数；两份文档各说各话的数字；以及"听起来合理但落不了地"的措辞。

评审方式是"逐块对比 + 逐点追问"：先把需求文档和技术方案做整体差异梳理，再按暴露出的疑点逐条澄清设计动机、边界和文档口径。所有产出收口成四类，每一类都有明确的去处：

| 产出 | 是什么 | 去处 |
|---|---|---|
| 修正 | 评审中当场改掉的文档错误 | 直接改两份文档，纪要里记结论 |
| 挂账 | 暂不决议、但不影响实现的开放问题 | 记入需求文档"未决事项"章 |
| 风险清单 | 可能出事的设计留白与排期隐患 | R1-R8 编号，一条条给应对与时点 |
| Action Item | 上面三类转化出的具体待办 | 按时点排期：第一周 spike / 实现期 / 阶段结束后 |

这四类的价值在于分工清楚：修正是"已经解决的"，挂账是"故意不解决的"，风险是"要防的"，Action Item 是"要做的"。很多项目的评审记录失败在把四者混成一锅"问题列表"，最后没人知道哪条还欠着。

### 2.2 一条修正的样本：一句落不了地的截断规则

概念先补齐。**上下文窗口**（context window）是大模型一次能读进来的最大文字量，超了请求直接报错。对话越滚越长，必须截断，于是需求文档里出现了这样一句规则："超过 LLM context window 上限时截断"。

听起来合理，评审却把这句判了死刑，理由只有一个问题：**这个上限从哪来？** 评审核对了整个设计——没有配置字段、没有"模型名 → 窗口大小"的元数据表、也没有调厂商接口探测的代码。一句规则的触发条件在整个系统里没有任何获取来源，它就是落不了地的空话。

修正后的口径变成：截断只看轮数，`max_history_turns`（默认 20 轮）是一个每个 Agent 可以自己配的参数，不探测窗口、不做 token 计量。这个机制技术方案里本来就是这么写的，需求文档那句是措辞漂移——所以定性为"措辞修正而非行为变更"。但它点出了一条硬纪律：**文档里每一句规则，都要能指出它的数据从哪来；指不出来的表述就是缺陷**。

同批修正的还有一处数字对不上：需求文档的目录树把 `agentos.db` 的表注释标错，"核心表"一处写 4 张、另一处写 6 张，建表时点的暗示也是错的。修正后两份文档统一为"6 张核心表 + 1 张条件表"，哪 3 张第三周建、哪 3 张第四周收尾，写死。报告在第 10 章把这类教训总结成三条纪律：同一数字两份文档必须同数；措辞不能欠定义；风险警示要落在权威章节并被交叉引用。

### 2.3 挂账：把"暂时不决定"变成资产

第二个反直觉的做法是"挂账"。评审中遇到暂时拍不了板的问题，不硬做决定，而是记成三条挂账，每条写清两栏：**现状**（当前规格里明确写死的做法）和**待决议问题**（将来要回答什么）。

| 挂账项 | 现状（照做即可） | 待决议问题 |
|---|---|---|
| 各触发源下的提示词（Prompt）组装策略 | 人推、钟推共用同一套组装 | 要不要按触发源差异化（记忆注入量、历史轮数） |
| 工具返回结果的裁剪策略 | 工具结果不论体积全量进会话历史，无上限 | 要不要加体积上限、压缩、淘汰 |
| GraalVM 引入时机 | 核心阶段不引入 | 何时引入 |

关键在第一条挂账的定性：**对实现者零歧义**。实现的人照"现状"栏做就行，不需要也不应该现在去解决那些开放问题。为什么不趁评审一起定了？报告答得很诚实：决议需要真实运行数据的输入——比如实测发现某些工具返回动辄几十 KB 挤爆上下文，才知道裁剪该怎么做。没有数据就拍板，拍的是空板。

配套机制叫"两文档互锁"：挂账记在需求文档的"未决事项"章，技术方案在对应位置补引用块标注现状与去向，两边一一对应。这样"未决"不会在实现时被误读成"没设计"。

## 3. 最重要的新发现：Spring AI 2.0 拆掉了设计依赖的开关

### 3.1 为什么一个框架开关能掀翻整体设计

这条被[报告](https://github.com/fangkun119/agent-os-poc/commit/d3ea9a37c14c79e8de376f4043002421427ad066/docs/review/001-tech-review-based-on-requirement.md)标为"评审最重要的新发现"（风险 R1）。讲清它要先补两个概念。

**ReAct 循环**是这类 Agent 系统的心跳：模型收到请求后，如果要查数据，就返回一个"我要调某工具"的请求；程序执行工具、把结果回灌给模型；模型再决定继续调工具还是给出最终回答。如此往复，直到任务完成。这个项目刻意选择**自己实现**这个循环，而不用框架自带的 Agent 抽象——因为工具调度的控制权必须握在自己手里。

问题来了。项目用的 Spring AI 框架自带一个开关 `internalToolExecutionEnabled`（内部工具执行开关），**默认开启**：框架在调用模型后会自动把工具执行掉。框架自动跑一遍，自研循环再跑一遍——同一个工具被调两次，整个循环设计作废。所以设计里钉死了一条红线：必须显式关闭这个开关。

而评审核验发现：Spring AI 2.0 已经把这个开关移除了。升级到 2.0，按 1.x 语境写的"自研循环 + 禁用自动执行"设计就失去了官方路径，工具调度段要按新机制重写。

### 3.2 结论、连锁影响与一次归因修正

评审给出的对策分三层：

| 层面 | 结论 |
|---|---|
| 版本锁定 | 锁定 Spring AI 1.0.x + SAA（Spring AI Alibaba）1.0.0.2 BOM（依赖版本清单，一处声明统一锁住全家版本）——这一线才有该开关 |
| 现存冲突 | 工程父工程是 Boot 3.5.16，SAA 官方验证组合是 3.4.5；要么降版本换官方组合，要么实测兼容并记入风险表 |
| 工程现状 | 全部 9 个模块的 pom 刻意不预引入 spring-ai，等第一周技术验证（spike）拿结论再引 |

值得一提的是评审里的一次自我纠错。评审前有过一句归因："ChatClient 会自作主张、ChatModel 不会"（两者都是 Spring AI 里调模型的入口，前者是高层门面，后者是薄接口）。经官方文档核验后修正：自动执行工具是**框架行为**，那个开关在两层都能设，不是 ChatClient 特有。修正之后，选 ChatModel 的真实理由反而更清楚了：一是控制点放在最薄的一层，循环不被任何高层封装的默认行为绑架；二是审计边界清晰——项目要求每次模型调用记一行流水（provider、模型、token 数、耗时），面对单次往返，这些数据拿得最直接。

这一节的可迁移结论：**当你依赖框架的"默认关闭"行为时，那个开关本身就是一个依赖项，要像依赖库一样锁定它的版本区间**。框架升级日志里一行"removed deprecated option"，就足以推翻一份设计文档。

## 4. 数据取舍的教科书案例：钟推会话的物理裁剪

### 4.1 问题：一个永远不换的会话，历史无限涨

先解释三个词。**Session** 是一次会话的容器，每条对话消息都追加进它的历史里，落库时存成 `sessions` 表的一列 JSON 文本（`messages_json`）。**钟推**是定时触发——cron（按时间表自动触发的调度机制）到点，调度器自动给 Agent 发一句话让它干活；与之相对的**人推**是人在命令行或 HTTP 接口里手动发消息。

钟推的会话有一个特殊设定：身份标识由"渠道 + 用户 + Agent 配置"合成，而钟推这两项固定为 `scheduler`。结果是**同一个定时任务的历次触发，永远复用同一个 Session**——这是故意的，昨天那次任务的上下文今天还能接上。

但代价随之而来：这个 Session 的历史只增不减，定时任务每几十分钟跑一次，三个月后 `messages_json` 会膨胀到不可收拾。评审纪要里把这个取舍写得很直白：每次落盘时，钟推 Session 的历史**物理裁剪**到最近 20 轮，更早的内容从数据库里删掉（见[报告 3.4 节](https://github.com/fangkun119/agent-os-poc/commit/d3ea9a37c14c79e8de376f4043002421427ad066/docs/review/001-tech-review-based-on-requirement.md)）。

这里要分清两个词：人推会话的截断是**逻辑截断**——库里的历史完整保留，只是每次拼请求给模型时只取最近 20 轮；钟推是**物理裁剪**——旧数据真的从库里消失。同一个配置参数（`max_history_turns`，默认 20）同时控制两处：改大它，模型看得更远，库里也留得更多。

### 4.2 补偿：把"完整留痕"移交给粒度更细的账本

裁掉的数据用什么补？项目里有两张审计表（流水账性质的表），在设计里明确"day one 就写入"——不是先打日志、以后再考虑入库：

| 表 | 记什么 | 写入时机 |
|---|---|---|
| `llm_calls` | 每次模型调用：provider、模型、token 用量、耗时 | 每次调用即时落库 |
| `tool_invocations` | 每次工具调用：入参、结果、成败、耗时 | 每次执行即时落库，成功失败都记 |
| `task_executions` | 每次定时触发：成败、耗时、关联的 session_id | 每次触发一行 |

这三张表与被裁的对话历史关键差异在写入时机：`messages_json` 是整个循环**结束后落一次**（避免反复重写一个大 JSON 字段）；审计表是**每调一次记一次**。所以对话流会被裁，账本永不丢——审计链这样串起来：一次定时执行 → 它的 session_id → 该会话下所有模型与工具调用记录。报告给了一个查账示例："每个 Agent 本月花了多少 token"，一句 SQL 按 session 关联就能算出来。

### 4.3 边界要诚实：审计不等于回放

你可能会问：那被裁掉的对话，能不能从审计表里还原出来？不能。这正是这条设计最值得学的部分——它把边界写得毫不含糊。`llm_calls` 只记调用元数据（provider、模型、token 数、耗时），**不存模型调用的输入输出文本**。靠着审计链能还原"那次定时任务跑了哪些调用、成没成、花了多少 token"，还原不出对话原文。

一句话概括这组取舍：**对话流可弃，审计链永在**。如果业务场景需要"回放某次定时任务的完整对话"，当前设计明确给不了——这句话写进文档，比含糊其辞要负责任得多。取舍三问（裁什么、拿什么补、边界在哪）都能答上来，激进的数据删除策略才是安全的。

## 5. 两条安全定案：不经解释器的执行，与被隔离的钥匙

### 5.1 shell 工具为什么不经过 bash：注入免疫从哪来

Agent 能执行 shell 命令，第一反应是危险：模型要是生成了一句 `git status; rm -rf /` 怎么办？这份报告把项目的对策讲成了一个经典案例——**不给命令任何被"解释"的机会**。

先看概念。操作系统执行程序的系统调用（exec）接收的是一个**参数数组**（argv）：`["git", "status"]`，每个元素原样作为一个独立参数，中间没有任何解释层。危险的是 shell（比如 bash）这个中间人——它会把 `;`、`&&`、`$()` 这些字符重新解析成控制符，把一条命令拆成多条执行。项目的设计是绕开这个中间人：

```java
// 不这么做：命令串交给 shell 解释，分号会被拆成两条命令
new ProcessBuilder("/bin/bash", "-c", "git status; rm -rf /")

// 这么做：argv[0] 是白名单里的程序本体，参数逐个传入
new ProcessBuilder("/usr/bin/git", "status").start()
```

执行前还按 `shell.allowed_commands` 白名单**精确比对**可执行文件的绝对路径（用绝对路径是防 PATH 劫持——攻击者把假 git 放进搜索路径前面）。校验通过才 exec。这样 `"status; rm -rf /"` 会作为一整个参数传给 git，git 不认识就报错，仅此而已。

报告同时如实记下了保留的口子：**参数内容本身不校验，只校验可执行文件**。所以设计文档里有一条被评审要求"原文要记住"的高危警示：把 python 这类解释器列入白名单，等于放通其全部文件与网络行为——`python -c "恶意代码"` 会重新打开解释层，文件白名单对它不生效。解释器默认禁用，列入属高危运维决策。

配套还有一条定性：项目里的 **Sandbox**（沙箱）不是隔离执行环境，只是工具执行前的白名单校验层——命名即定性，实现类干脆叫 `SandboxChecker`（检查器）。报告原话："劝阻级防线，防不住蓄意绕过"。真正的容器级隔离留给扩展阶段另立的接口，不让一个白名单接口假装两种能力。

### 5.2 notify 的独立白名单：把钥匙和锁分开

第二个安全定案关于消息推送。Agent 跑完任务要把结果推到企业微信群这类 IM 群机器人，走的是 **webhook**——一种"往一个 URL 发一个 POST 请求就完成推送"的机制。麻烦在于 webhook 地址自带凭证：形如 `https://qyapi.weixin.qq.com/...?key=693a...`，那个 `key` 就是门钥匙，拿到它任何人都能往群里发任意消息。

项目的推送目标是集中登记在一张全局注册表（`notify_channels`）里的，Agent 只按名字引用，URL 不进对话。推送出网前要过域名白名单——而评审确认的设计是：推送走**独立白名单** `notify.allowed_domains`，与普通 HTTP 工具的 `http.allowed_domains` 分离。

为什么不能共用一份？报告列出的风险链值得逐环看：

1. **钥匙会回流进上下文**：推送的错误信息、重试日志可能带着完整 URL，以工具消息的形态进入会话历史——模型的上下文里就有了这把钥匙；
2. **普通 HTTP 工具变成伪造通道**：一旦模型被诱导（提示注入）或行为异常，`http_post` 因为同域在白名单内，可以直接打到 webhook 地址——拿着上下文里的 key 仿冒 Agent 往群里发假告警、钓鱼消息；
3. **运维无法分账**：一份清单两种用途，想"锁死普通 HTTP、只留推送"做不到。

独立白名单之后互不传染：key 即使泄漏进上下文，`http_post` 也被域名挡在门外。这本质是一个**最小权限**原则的变体：不是"这个域名能不能访问"，而是"这个工具访问这个域名的**目的**是否被授权"——同一域名，拉数据（get）和送凭证消息（notify）是两种权限，分开授。项目甚至把 notify 做成了与 `http_get`（拉数据）、`http_post`（办事）并列的第三个工具，一句话记忆：get 拉数据、post 办事、notify 报信。

## 6. 其余定案速览

报告 10 章里还有大量已拍板的设计点，逐一深讲会失焦，合并在一张表里。每一项在纪要中都有对应的论证与边界说明：

| 主题 | 定案 | 一句话理由 |
|---|---|---|
| 存储选型 | SQLite 单文件，不用 H2 | 数据以标准文件落盘，任意工具能直接查——对应"数据留企业、随时可人工核查"；代价是接受平台相关的本地库 |
| 核心记忆区 | 永不截断、无删除 | 靠结构性隔离强制：裁剪代码的作用域天生够不到核心区（那条 SQL 里没有 LIMIT） |
| 记忆注入 | 每轮现读、不缓存 | 若启动时注入一次，"记住用户偏好"会退化成"下次重启才生效" |
| 记忆零拷贝 | 注入 ≠ 存进历史 | 记忆只进每次现拼的请求，不落库；存储层拷贝数为 0 |
| 定时任务定义 | 只认 Agent 配置文件，不给创建 API | 文件是源头、数据库表只是状态影子；API 改不了源头 |
| 工具连接配置 | 走 `mcp_servers.yaml` 文件 | 用户主动维护的数据要可编辑、git 可跟踪；运行时动态注册的才落库 |
| 模型对接层 | 落在最薄的 ChatModel 接口 | 控制权 + 审计边界；不用 SAA 自带的编排框架，避免锁进它的编排模型 |
| 排期风险 | 最重的一条线押在第四周 | 定时任务 + 推送 + 8 端点 + 三表 + 两个演示全在 W4；降级预案已论证 |
| 降级交付 | W1-W3 产物自洽可先行交付 | 主线四对前面是单向依赖，砍掉损失惊艳度不损失可用性；代价是四项发布硬条件无法打勾 |
| 元发现 | 需求文档曾滞后于技术方案 | 五处"技术方案设计完了、需求文档没跟上"同属一个病根；纪律是改设计必须同步需求文档 |

## 7. 收尾：能搬走的四件事

这次变更没有改一行业务代码，改的是"实施前对齐"这件事本身。四条可以直接搬走：

1. **措辞可落地性检查**。评审里最有杀伤力的问题不是"这设计对吗"，而是"这句规则的数据从哪来"。让每条需求规则都能指出它的配置项、字段或接口来源，指不出来的就是缺陷。
2. **挂账是资产，不是欠账**。暂不决议的问题，写成"现状（照做即可）+ 待决议问题 + 决议时点"三栏，再在关联文档处互锁标注。实现者零歧义，决议者有据可查。
3. **框架默认行为是依赖项**。依赖一个"默认关闭"的开关，就锁定它的版本区间；升级评估时把"移除的选项"当破坏性变更对待。依赖一个默认开启的行为（如自动工具执行），先确认它和你的架构是否兼容。
4. **取舍三问**。任何激进设计（比如物理删除会话历史）都要答得上：裁什么、拿什么补、边界在哪。答案写进文档，比含糊其辞安全。

操作层面的迁移建议：第 2 章那张"修正 / 挂账 / 风险 / Action Item"四类产出表，可以直接当评审模板用；风险清单的格式（编号、说明、应对与时点）也照抄即可，R1-R8 一共八条，条条有着落。
