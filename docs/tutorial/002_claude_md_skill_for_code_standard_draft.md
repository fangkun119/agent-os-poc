# 用 1558 行 Markdown 造一条"编程规范"生产线：claude-md-draft-for-code-standard 技能包全解

## 1. 代码全貌：一套给 AI 立规矩的流水线

先交代两个背景概念。

**CLAUDE.md** 是 AI 编码工具（如 Claude Code）每次开工时自动加载的项目指令文件，相当于新员工的入职手册：构建命令、目录结构、"不要做 X"之类的约定都写在里面。手册质量直接决定 AI 干活的质量——但多数项目要么没有，要么塞满过时内容。

**Skill（技能包）** 是 Claude Code 的一种扩展机制：一个目录，里面放一份 SKILL.md 主文件和若干参考资料。用户提到相关任务时，AI 加载这份主文件，按其中的流程干活。

本目录就是一个完整的 skill：**claude-md-draft-for-code-standard**。它的职责是替你起草 CLAUDE.md——读你的代码或会话复盘、按需调研官方文档、抽取候选规范条款、逐条评分、对抗评审，最后产出一份带完整论证链、不超过 200 行的草稿。草稿落在 `consolidate/` 目录供人裁决，**skill 永远不直接写仓库里的 CLAUDE.md，也不改任何被治理的源码**。SKILL.md 里有一句定位口号："把流程交给 Skill，把裁决留给人。"

你可能会问：AI 本身就会写规范，为什么还要一台"生成器"？这套代码的回答是：AI 直接写的规范是拍脑袋，每条条款说不出"证据是什么、为什么值得写、AI 为什么会犯这个错"。整个 skill 的设计核心就是把这三个问题变成流水线上的强制关卡。下面按流水线顺序逐个文件拆解。

## 2. SKILL.md：一份用 Markdown 写成的流程引擎

### 2.1 frontmatter：让 AI 知道什么时候唤醒这套流程

**是什么**：SKILL.md 开头 10 行是 **frontmatter**（两道 `---` 之间的 YAML 配置块，一种"键: 值"格式的配置写法）。四个关键字段各司其职：

| 字段 | 值的要点 | 作用 |
|---|---|---|
| `name` | claude-md-draft-for-code-standard | 技能包唯一名 |
| `description` | 一段约 300 字的长描述，穷举触发话术与路由规则 | 用户说"给项目立代码规范""按 pom.xml 推技术栈立规"时命中本 skill；说"日常更新既有 CLAUDE.md"时主动让位给姊妹 skill |
| `argument-hint` | [输入来源（可多源叠加）：目录/文档路径或技术栈口述] | 提示用户调用时要带什么参数 |
| `metadata` | author / version | 维护信息 |

**为什么这样设计**：`description` 写得极长是刻意的。skill 靠语义匹配触发，描述里每多写一句典型用户话语（"这份阿里规范直接当判例用、别调研"），误触发和漏触发就少一分。末尾还写明了与姊妹技能 claude-md-draft-for-tech-constrain 的分界——那边从设计文档提炼架构约束，这边从技术栈和实战证据提炼编码规范。让 AI 在触发阶段就完成分流，比跑错流程后再纠正便宜得多。

### 2.2 六类输入来源：开放集设计

**是什么**：SKILL.md 的"输入来源识别"节用一张表定义了六类输入源，编号 SRC-1 到 SRC-6：

| 编号 | 来源 | 能产出什么 |
|---|---|---|
| SRC-1 | 已有代码目录 | 技术栈 + 实测踩坑（证据最硬） |
| SRC-2 | 会话记录与事故复盘 | 踩坑记录 + 组件清单 |
| SRC-3 | 库依赖清单（pom.xml / package.json 等） | 仅技术栈 |
| SRC-4 | 技术栈口述（"给一个 Go CLI 项目立规"） | 仅技术栈 |
| SRC-5 | 项目约束文档（SPEC、AI 编程指南等） | 技术栈 + 约束红线（直入骨架） |
| SRC-6 | 现成编程规范文档（阿里巴巴 Java 手册、Google Java Style） | 本地判例，排他 |

**为什么这样设计**：表中"能产出什么"一列是关键——来源被登记为能力而不是类别。SKILL.md 明文写"来源是开放集：不预设三选一，运行时逐源识别、按「能产出什么」登记能力"。多源叠加是合法且常态的（比如代码目录 + 一份 SPEC），唯 SRC-6 排他。这套编号在所有细则文件中通用，成为整套代码的公共语言。

同节还有一条容易忽略的纪律：**落点既有的 CLAUDE.md 不是输入源**。自动扫描不发现它，用户显式提供也不登记为生产原料——它只在最后一步做事后对照。这条纪律防的是"新规范抄旧规范"的自我循环，第 5 章会看到它的配套披露机制。

### 2.3 主分叉：要不要调研，一步判定

**是什么**：全流程唯一的分叉点，判据只有一句话——输入里有没有现成编程规范文档（SRC-6）。

- **支路一（没有）**：走完整流程——盘点代码 → 爬取官方判例落盘 → ③-⑨。
- **支路二（只有它）**：跳过盘点和调研——把用户给的规范文档拷入工作区登记为"本地**判例**"（这套代码对"落盘留存的规范原文"的称呼，是后续抽取条款的唯一依据），之后 ③-⑨ 全量照走。用户只给阿里巴巴手册，就只从中提取条款，不补其它技术栈（"不补差"）。
- **混合输入直接退出**：SRC-6 与其它任一来源并存时提示不支持，建议按技术栈拆成多次运行。

**为什么这样设计**：分叉的本质是把"资料已在手上"和"需要出门找资料"两类运行分开。支路二全程零网络请求，天然不受第 3 章的网络门控约束；failure-modes.md 第 9、10 条专门登记了这一分叉的两种翻车方式（支路二误触发调研、混合输入未排他），并规定命中即纠正、禁止静默忽略。

**怎么用、影响什么**：作为使用者，你给什么输入决定了跑哪条支路——扫描一个现有代码仓库，得到的是"从你的坑里提炼"的规范；丢一份阿里手册，得到的是"从业界规范里筛出适合 CLAUDE.md 的子集"。同一段 ③-⑨ 后续流程两条支路共享，差别只在原料从哪来。

### 2.4 步骤契约表：主文件只写"做什么"，细则按需翻

**是什么**：SKILL.md 的主体是一张 ⓪-⑨ 十一步的契约表，每步四列：执行条件、产物、契约要点。流程骨架是：

```
⓪ 落点拍板 · 来源登记 · 分叉判定
 ├─ 支路一 → ① 盘点 → ② 全量调研落盘
 └─ 支路二 → 拷入登记本地判例（跳①②）
      ↓ 汇合
③ 条款抽取与评分 → ④ 对抗验证 → ⑤ Action 识别 → ⑥ 终选分组审议
 → ⑦ 起草初稿 → ⑧ 三路对抗评审 → ⑨ 修订落盘 + 汇报
```

契约要点列常见"独立 sub agent"字样。**sub agent** 指主流程派出去、在独立上下文里干活的子任务：盘点是一个 agent，抽取按判例文档分组各派一个，评审另派三个（并发上限 8，即 **fan-out**——同时派出的子任务数——上限，防止请求过载被限流）。

**为什么这样设计**：SKILL.md 只有 137 行，却要承载十一步流程。它靠"主文件写契约、细则写操作"的分工做到：契约表里每步只写"条件-产物-要点"，表后附一节"references/ 使用指引"，标明每个细则文件在哪几步该被读。这对应一条元规范（第 6 章详述）：子目录文件按需加载，所以主文件必须自足能跑通全程，细则文件也必须各自自足——只读那一个文件就能完成该步职责。每份细则开头都有一段"本文件职责 / 上游 / 下游"引言，就是自足性的落地。

**怎么用、影响什么**：想定制这套流程，入口就是这张表——加一步、改一步的产物契约，主文件一处改动即可；细节实现则在对应细则文件里。这种"总纲 + 分册"的结构让 1558 行没有一处需要一次读完。

## 3. sources.md 与 scoring.md：条款凭啥入选——证据链先行

这两份细则合起来回答选材问题：sources.md 管原料从哪来、怎么登记，scoring.md 管候选怎么筛、怎么打分。合在一章讲，因为它们是一根因果链——来源判型决定证据等级，证据等级封顶评分。

### 3.1 证据分级 S1-S5：给"坑"验明正身

**是什么**：scoring.md 第 1 节把条款证据分五级，每级规定"必要性"维度的打分上限：

| 等级 | 名称 | 来源 | 必要性封顶 |
|---|---|---|---|
| S1 | 事故级 | 代码实测或事故复盘记录的真实事故 | 可给 5 |
| S2 | 盘点级 | 实测违反但未酿事故 | 4 |
| S3 | 指南级 | 项目约束文档明文 | 3 |
| S4 | 判例级 | 落盘的业界规范原文 | 3 |
| S5 | 推断级 | 模型知识无出处 | 默认不支撑正文 |

**为什么这样设计**：类比法庭证据——现场物证强于目击证言，目击证言强于传闻。S1 要求"附可复核实况：file:line 或复盘原文引用"，S3 有句防伪条款"指南记录的坑不得冒充实测"。设计意图是让"这条规则多重要"不再由 AI 的语感决定，而由证据的硬度封顶：再耸人听闻的推断级条款，也进不了正文——只能进"**待沉淀节**"（草稿正文之后的一个条件小节，专门收容暂无证据、列明"满足什么判据才升入正文"的候选条款）。

同节还有一条精细的"**转写强度对齐**"纪律：条款的措辞强度不得超过源证据的承载。判例原文写 "should most likely be avoided"（建议避免），条款就不能写成"禁通配符关键选择器"（绝对禁令）——保真不只保内容，也保语气。理由写在文件里：条款强于证据时，按字面执行会误伤合法场景。

### 3.2 准入一票筛：不可判的直接出局

**是什么**：评分之前的闸门。只收"有客观违反判据"的条款，判据三选一：有代码仓库就以"对照 git diff 能看出违反"为判据；有约束文档就以指南原文为判据；只有判例就以落盘原文为判据。四类直接出局：不可判、裁量性、触发面为空、可从代码推导。出局条目记入否决清单，不许悄悄消失。

**为什么这样设计**：文件里有一句精彩的分工声明，值得整段理解——"准入一票筛只问「可判吗」（客观性）；证据分级 S1-S5 只问「坑是真的吗」（真实性）；四维评分中的 AI 犯错要件只问「AI 会犯吗」（相关性）；重 / 扩管「值多少」，合管「写得清」。各判据只回答各自的问题，不互相替代、不重复检查。" 把一道模糊的"这条规则好不好"拆成五个正交问题，是这套代码最值得借鉴的评审思维。

"可从代码推导的直接出局"初看反直觉：规范不就该管代码风格吗？这里的依据来自第 6 章的元-6——AI 自己读仓库就能知道的事（目录结构、依赖清单），写进指令文件只浪费篇幅。

### 3.3 四维评分与 AI 犯错要件

**是什么**：过了准入的候选进入打分。公式：**综合分 = 必×0.3 + 重×0.3 + 合×0.2 + 扩×0.2**，四舍五入到 0.5。四维各 1-5 分：必（必要性，受证据分级封顶）、重（违反后果严重度）、合（可执行性——能否构造一行可 diff 的违反判据）、扩（触发面广度）。

**为什么这样设计**：这套公式最有意思的地方是"必"维的第二要件——**AI 犯错要件**。打分前必须写出"AI 为什么会犯这个错"的一句话机制（长上下文遗忘、幻觉出不存在的配置键、禁令字面执行过宽……），写不出机制且无实证的，"必"最高只能给 2。文件写明了理由：CLAUDE.md 的读者是 agent，"AI 不会犯的坑写进去只占行数、稀释遵从率"。纯人类的审美偏好（AI 在格式化工具约束下根本不会犯）在这里被系统性清除。

你可能会问：为什么不直接照抄官方 best practice？scoring.md 第 6 节的"双写规则"给出了更细的答案——当官方说法与项目现实冲突时，必须两处都写：正文写显式例外条款（防止 AI 拿官方文档批量"修正"项目代码），勿再加清单里记否决理由（防止后人重复论证）。"只写其一即缺陷"。

另一处值得注意的设计痕迹：四维定义下方括注着"历史缺口：「重 / 合 / 扩」曾未定义，迫使运行时即兴仲裁"——这条注释说明该文件是从实际运行中迭代出来的，缺什么定义补什么定义。

### 3.4 调研的门控与降级：网络失败不等于证据失败

**是什么**（sources.md）：支路一第②步要爬取官方文档，sources.md 规定了三条硬纪律：

- **门控**：爬取前先检查 firecrawl（一款网页抓取工具）可用，不可用就停下提示，不静默降级；这是整个 skill 唯一的工具绑定。
- **总量封顶**：判例 20-30 份封顶，超出按"官方一手 > 二手 > 社区"裁剪，被裁项记入未下载清单。
- **降级语义**：验证失败的判例标 `fetch_failed`（未能核验），**禁止判死链、禁止一票否决**——抓取失败可能是执行环境拦截，不等于 URL 失效。

**怎么用、影响什么**：这套登记纪律的效果在第 8 步兑现——评审引用判例时"必须回查落盘原文，禁止凭记忆引用"，回查不依赖 URL 可达性。证据一旦落盘，后续所有环节都对着同一份不可变的原文工作，争论有据可查。

### 3.5 两套档位线与终选审议

**是什么**：评分之后有两次取舍。第③步用讨论稿档位线打初档：≥4 固化、2.5-4 一行提及、<2.5 不添加。第⑥步是独立步骤，用终选线分组议决：≥4 入正文；2.5-4 逐条合议；一行提及的看能否三条并一簇。淘汰必须记死因四值——因果链自相矛盾 / 触发面为空 / 覆盖被占满 / 机制含混——外加一组"特征 token 集"（可用于检索的主题词）。终档后还要按综合分升序排好"牺牲顺序"，为第 4 章的 200 行红线做准备。

**为什么这样设计**：初档与终档分离（scoring.md 称之为对历史缺陷 MF-1 的仲裁），是因为起草必须"一律以⑥终档为准"——没有这条，起草者可能拿着过时的初档写作。而"特征 token 集"看似琐碎，实为第 5 章"回潜 grep"的数据源：被否决的条款要防止改头换面溜回正文，前提是否决时就留下可检索的指纹。

## 4. template.md：草稿长什么样——五段骨架与红线九条

### 4.1 五段骨架与 200 行预算

**是什么**：template.md 第 2 节规定终稿的五段结构，各归其位、不得换序：

| 段 | 内容 | 要点 |
|---|---|---|
| 1 文件头 | 适用范围 / 技术栈 / 效力锚 | 效力锚一行声明：本文件是草稿，与既有 CLAUDE.md 冲突时以既有文件为准 |
| 2 固化骨架 | 条件段，仅当有 SRC-5 红线时存在 | 约束红线免评分直入，保留原文口径 |
| 3 入选正文 | 终选 ≥4 的条款 | 每条带候选 ID（`C-{nn}`），可回查证据链 |
| 4 提示区 | 自描述演进纪律 | 写明"同类错误重复出现才增条"等增条门槛 |
| 5 块级 HTML 豁免注记 | 状态块等人类专用信息 | 整段放 HTML 注释里，不计行数 |

行数红线 ≤200，口径唯一且机械：全文行数减去以 `<!--` 开头的行数，实测方法写死为 `wc -l` 减 `grep -c '^<!--'`，禁止各步自创口径。落盘时记录三个数：红线 200 / 估算 / 实况。

**为什么这样设计**：200 不是拍脑袋的整数，官方文档原文口径是"超过 200 行的指令文件消耗更多上下文并降低遵从率"（第 6 章会看到随包原件里的原句）。而"减 HTML 注释行"这个怪口径，对应一个真实的加载器行为：Claude Code 在把 CLAUDE.md 注入 AI 上下文前会剥离块级 HTML 注释——所以注释区是"人能看、AI 看不见"的免费空间。状态块（十余个字段的运行元数据）塞在这里，既留全了论证链又不占 AI 的注意力预算。

**怎么用、影响什么**：超行时不平均压缩，而是按"牺牲顺序"裁——综合分升序淘汰，4.0 分档不动。评分体系在此闭环：第 3 章打的分，决定了超预算时谁先出局。

### 4.2 红线九条：写规范的规范

**是什么**：template.md 第 3 节列出起草时逐条不可违反的九条红线。摘最有特色的三条：

- **无腐烂信息**：正文无行号、无日期、无项目品牌名与内部路径。理由写在配套说明里——"旧行号诱导把已修复项当缺陷复改"；行号只允许存在于工作产物，且必须标注快照基线（日期 + commit 短哈希）。
- **条件式 + 站点参数清单**：站点特定的取值不硬编码进条款，而是抽成编号键值对表（每行含参数名 / 当前值 / 状态 `SET` 或 `PENDING` / 影响条款 / 建议默认值与依据）。未定参数在正文以 `TODO(参数名): 用途` 占位，"质量梯度写在空格数上"。
- **命令红线**：写进草稿的命令必须可安全重复执行，禁 `make clean` 和一切删除覆盖类命令——手册里的命令会被 AI 反复执行，破坏性命令等于埋雷。

**为什么这样设计**：九条红线共同防的是同一类病——把"一次性快照"写成"永久真理"。条件式 + 参数清单是官方文档建议的通用化写法在本场景的具体化；template.md 同时点名禁掉两种歪路："删光站点内容写正确的废话"与"硬编码站点取值"——前者形式通用但没用，后者有用但换个项目就错。

### 4.3 状态块与中间产物七件：论证链归档

**是什么**：template.md 第 4 节登记了运行全程产生的七个中间产物文件（落 `draft/` 工作区）：inventory.md（盘点证据）、research-index.md（判例索引）、candidates.md（候选与评分表）、adversarial.md（对抗改判记录）、actions.md（工单）、final-selection.md（终选与否决清单）、review.md（评审记录）。状态块则以字段表形式记录落点、来源组合、基线、未决参数、行数三数、"条款 ID ↔ 评分表 rank"映射等。

**为什么这样设计**：唯一交付物只有一页草稿，但它必须是"可审计的"。正文条款不带出处（省行数），溯源走状态块的 ID 映射：读者看到 C-07 条款，经映射回查 candidates.md 的评分表，再经评分表回查判例原文或盘点证据。整个链条上每一步结论都有文件承接，事后任何一条都能回答"你凭什么立这条规"。对比一下：让 AI 直接写一份规范，产出物没有这条链，争议时无从查起。

### 4.4 只识别不修复：工单移交

**是什么**：盘点发现代码里确实存在乱象时，流程第⑤步不开药方，而是开**工单**——每个工单六个字段：现象 / 判据 / 建议修法 / 验收四段（可构建、产物或测试可核、运行时可探活、资源可回收）/ 范围红线（逐项列"不要顺手修"的诱惑）/ 尝试次数上限。运行结束汇报必须列出全部工单摘要，修不修由用户裁决。

**为什么这样设计**：这是"把裁决留给人"的边界条款。template.md 写明"skill 只识别、开单、移交用户：不改被治理代码、不跑清理构建"。"范围红线"字段尤其有意思——它预设了执行修复的一方（可能是另一个 AI 会话）会顺手扩大战场，所以提前逐项列出"不要动什么"。

## 5. review.md 与 failure-modes.md：对抗性质量机制

你可能会问：评分、终选都过了，为什么还要再评一轮？因为前两关管的是"选材"（条款值不值得写），第⑧步管的是"写法"（条款写得对不对、会不会被误读）。selection 和 rendering 是两类缺陷，前者查不出后者。

### 5.1 三路评审与五项恒定检查

**是什么**：第⑧步默认派 3 个独立上下文的评审 agent（预算敏感时经用户确认可降级为单 agent 三轮换视角，无人值守时允许自动降级但必须在产物中声明、覆盖面不得裁剪）。五个检查项固定：

1. **通用性泄漏**——双向检查：站点信息写死进正文是泄漏；为避泄漏删成"正确的废话"是空洞化，两个方向都算失败。
2. **AI 可执行性**——对每条禁令做字面执行推演，且必须逐条构造反例场景留痕（"一个按字面执行会被误伤的具体合法场景"），构造未果也要显式记"构造未果"，不许笼统写"未发现问题"。文件里留了真实判例：初稿写"模板禁内联 style 与行内事件"，"行内事件"字面执行会封死一切交互组件，终稿收窄为只禁内联样式属性。
3. **人类可读性**——bullet 密度、粗体导语、术语首现括注。
4. **回潜 grep**（下一小节）。
5. **自举合规**（再下一小节）。

**为什么这样设计**："独立上下文，禁起草者自评"是硬规定。作者看自己的稿子有盲区——review.md 举例：must_fix 级的"禁内联事件措辞"正是由独立视角抓出的。发现分两级：`must_fix` 阻断落盘（全部修复才能进第⑨步，**fail-fast**——出错即停、不带病前进），`suggest` 逐条显式采纳或驳回，禁止静默忽略。

### 5.2 回潜 grep：用确定性检索替代肉眼

**是什么**：检查"终选已否决的条目是否悄悄写回初稿"。操作五步固定：从否决清单提取特征 token → 逐 token 在初稿全文检索 → 判定命中行是否属于 HTML 注释区（唯一白名单）→ 命中的只有两个出口（删除，或引用既有死因显式改判）→ 逐 token 落盘检索记录，零命中也要记"未命中"。文件记载的真实战果：已否决的「Be consistent」条款曾被评审抓出写回初稿。

**为什么这样设计**：关键词是"确定性"。靠评审员通读记忆去发现"改头换面的旧观点"极不可靠；把否决时的特征 token 攒下来，用机械检索兜底，把主观遗漏变成可复算的检查。落盘"零命中也逐 token 记录"则让检查本身可审计——没查和查了没中是两回事。

### 5.3 自举合规：草稿要遵守自己立的规矩

**是什么**：把草稿自身立出的全部规则（含提示区的演进纪律）逐条编号，逐条检查草稿文本自己是否遵守。判定三值：合规（须指出至少一处自检过的文本面）/ 违反（一律 must_fix）/ 不适用（须写明理由，"禁止用不适用掩盖可检未检"）。真实判例：初稿自己写了小写 css/yaml，被自己的"专有名词大小写"条款抓出。

**为什么这样设计**：规范文件最大的信誉风险是双标。让草稿过一遍"自己抓自己"，既堵住最尴尬的缺陷，也顺带验证了每条规则"可判"——一条无法对草稿自身执行的规则，多半也无法对用户代码执行。

### 5.4 终局机检与失败模式登记表

**是什么**：第⑨步落盘前还有五项机械检查：指针闭合（正文所有"见 C-xx"类指代目标必须真实存在）、条款冲突扫描（同一配置键话题簇内指令方向必须相容）、TODO 键名逐字相等、PENDING 参数行的字段格式、行数三数复核（按唯一机械口径重算）。命中一律按 must_fix 处理——机检项全是客观判据，没有 suggest 档。最后按固定六项格式汇报（终稿路径 / 三行数 / 来源组合 / 未决参数 / 工单清单 / 遗留规范对照摘要）。

failure-modes.md 则是全程的防御工事：14 条失败模式，每条三段式——症状（如何识别）、预防规则（命中后必须执行）、来源条款。覆盖面从网络（限流 429 就分批、并发上限 8）到语义（条款强度超出证据承载）到机制（上游 agent 返回 null 导致下游解引用崩溃）。第 14 条尤其坦诚：**注入污染**——落点目录已有 CLAUDE.md 时，运行中读取目录内文件会被 harness 自动注入既有内容，"⓪-⑧不读"的文字纪律拦不住这种底层行为。设计选择不是假装能根治，而是强制披露：状态块记"对照受注入污染风险"，对照结论标注"仅供人工参考，不作为合并唯一依据"。

**怎么用、影响什么**：这一章的设计对任何"AI 产出 + 人工把关"的流程都可迁移——分级处置（must_fix / suggest）、确定性检查兜底主观审查、自举合规、对系统性盲区做显式披露而非隐瞒，四件事都不依赖 Claude Code。

## 6. meta-norms.md 与两份随包原件：元规范为什么预打包

### 6.1 六条元规范：写 CLAUDE.md 本身是门学问

**是什么**：meta-norms.md 汇总了六条"怎么写 AI 指令文件"的规范，每条四件套——规则（祈使句）、可检验判据、设计文档引用处、原件出处：

| 条 | 规则 | 一句话理由 |
|---|---|---|
| 元-1 | 单文件正文 ≤200 行 | 超长消耗上下文、降低遵从率，是阈值不是配额 |
| 元-2 | 无矛盾条款 | 两条规则冲突时 agent 可能随机执行其一 |
| 元-3 | 同类错误重复出现才增条 | 单次偶发不增条，优先并入既有条目 |
| 元-4 | 人类专用信息只进块级 HTML 注释 | 注释在注入前被剥离，不占 AI 注意力 |
| 元-5 | 按需加载的文件必须自足 | 子目录文件被读到时才进上下文，悬空引用会断链 |
| 元-6 | 能从代码推导的不写 | 只写三类：坑、理由、与工具默认值不同的约定 |

**为什么这样设计**：注意这六条与"代码怎么写"完全正交——用户丢来一份阿里巴巴 Java 手册，里面没有任何一条教你怎么写 CLAUDE.md。所以这条"元规范路"在全流程恒定保留，不受支路分叉影响。第 2 章说的"细则文件自足"、第 4 章的"200 行口径"、第 3 章的"可推导内容出局"，全部根植于此——元规范是整套代码的宪法层。

### 6.2 随包原件：每条规则都有出处

**是什么**：references/ 下躺着两份"原件"：claude-code-memory.md 是 Claude Code 官方 memory 文档的完整快照（头部两行标注 `> Source: https://code.claude.com/docs/en/memory` 与 `> Downloaded: 2026-08-28 via Firecrawl`），504 行里连网页导航栏都原样保留；agentsmd-spec.md 是 AGENTS.md 开放规范的快照，定义了"agent 版 README"的推荐章节（Setup commands / Code style / Testing instructions / PR instructions）。

**为什么这样设计**：meta-norms.md 第 0 节交代了预打包的权衡——"元规范更新频率极低（季度级）。预打包比运行时反复爬取更稳——零网络依赖、零失败面、版本随 skill 升级同步更新"。这就是第 2 章网络门控的由来：门控只挂"支路一的第②步调研"，元规范读本地、判例拷入本地都不触发。连原件为何不精简也有答案（打包说明一节）：保留全文是为了让运行 agent "引用可回查原文全文，不依赖本文件第 1 节的转述"。504 行的导航噪音是换取可回查性的代价。

你可能会问：为什么不每次运行时去爬最新版官方文档？除了门控与稳定性，还有一层证据纪律：判例一旦落盘就是本次运行的固定证据基面，评审回查的是同一份原文；若每次现爬，证据在流程中途漂移，"禁止凭记忆引用"就失去了锚点。

**怎么用、影响什么**：这条"原件 + 索引 + 转述"三层结构（原件存全文、meta-norms.md 做索引与六条口径、草稿引用时回查原件）是可以直接搬到任何"AI 需要引用权威文档"的场景的——把文档快照随包携带，引用纪律定为"必回查原文、禁凭记忆"，幻觉引用的空间就被压没了。

## 7. 收尾：这套代码真正教的事

回看全流程，这台"规范生产线"反复在做同一件事：**把模糊判断拆成可检验的关卡**。

- "这条规范好不好" 拆成五个正交问题（可判吗 / 坑是真的吗 / AI 会犯吗 / 值多少 / 写得清）。
- "写出来的稿子行不行" 拆成五项恒定检查，其中两项（回潜 grep、行数口径）干脆机械化了。
- "这个 skill 靠谱吗" 拆成 14 条失败模式的症状与预防规则。

三件最值得迁移的设计：其一，**证据分级封顶评分**——任何"AI 帮我做判断"的流程，都该先问证据从哪来、多硬，再谈权重。其二，**对抗与自举**——独立上下文评审、草稿遵守自己立的规矩、确定性检索兜底，这套组合拳与具体领域无关。其三，**人与 AI 的边界**——skill 生产带完整论证链的草稿，落盘、修复、合并全由人裁决；发现的缺陷开工单移交而不是顺手改掉。边界画得越清楚，自动化越敢往前推。

限制也要如实说：整套流程没有可执行代码，每一步的"强制力"来自提示词纪律而非程序校验（终局机检五项里真正机械的只有行数口径一项）；上游设计文档 skill-design.md 被各文件反复引用却不在本目录，多数仲裁记录只能看到结论看不到过程。它是一套流程宪法，不是一台不依赖执行者素质的机器。
