# 给 AI 编程助手立"规矩"的规矩：解剖一个 170 行的 Claude Code Skill

用过 AI 编程助手的人多半遇到过这类烦恼：AI 每次会话都"失忆"，把项目约定忘个精光；你反复纠正的坑，它换个会话接着踩。业界的通行解法是给项目放一份常驻说明书（CLAUDE.md），让 AI 每次开工先读它。但这份说明书本身怎么写才不会过期、不会和别的文档打架、不会被 AI 当成权威乱传？

本篇解剖的正是一个回答这个问题的"程序"：`.claude/skills/claude-md-draft-for-tech-constrain/` 目录下的 [SKILL.md](https://github.com/fangkun119/agent-os-poc/commit/3869e7b5d46bea5cadaddaffcafc47f9f462e30e/.claude/skills/claude-md-draft-for-tech-constrain/SKILL.md)。它把"为 AI 助手写项目说明书"这件事本身，做成了 AI 可以执行的工作流。我们会逐节讲清它是什么、为什么这样设计、怎么用、影响什么——顺带把 Claude Code Skill（技能包）这套机制教会。

## 1. 代码全貌：一个 170 行的"提示词程序"

这套代码的全部内容是一个 SKILL.md 文件：170 行 Markdown，前 10 行是 YAML 配置（frontmatter），后 160 行是给 AI 读的操作指令。它定义了一个名叫 `claude-md-draft-for-tech-constrain` 的 Claude Code Skill，职责一句话：扫描项目已有的设计文档（需求、技术方案、README 等），提炼出一份 CLAUDE.md 草稿——回答"这个仓库是什么、什么不能做"——草稿放进 `consolidate/` 目录，等人工裁决后自行拷入。

两个前置概念，零基础读者看这里就够：

| 概念 | 一句话解释 | 类比 |
|------|-----------|------|
| CLAUDE.md | 放在仓库根目录的说明书，AI 编程助手每次会话自动读取注入上下文 | 员工入职第一天发的《新人须知》 |
| Skill（技能包） | 把一套工作方法写进 SKILL.md，让 AI 按它执行；人可用斜杠命令调用，模型也可按描述自动触发 | 把老师傅的操作规程写成标准作业书 |

所以这份文件的性质是"提示词即程序"：对 AI 的自然语言指令就是源代码，章节就是模块，条款就是语句。它的模块清单如下（行号对应仓库里的文件）：

| 模块（文中的节） | 行号 | 职责一句话 |
|---|---|---|
| 元数据头（frontmatter） | 1–10 | 声明名字、触发时机、调用方式 |
| 目标与边界 | 12–22 | 定职责：只产草稿、只读源文档、永不写落点 |
| 输出路径与占位符 | 24–41 | 规定产物落哪、怎么命名、撞名怎么办 |
| 不变量 | 43–50 | 六条任何项目都必须遵守的质量判据 |
| 默认值 | 52–54 | 可偏离的体量与形态基线 |
| 执行流程（第 1–6 步） | 58–129 | 从盘点文档到汇报产出的完整流水线 |
| 必问清单 | 132–140 | 固定 5 项必须问人的事 |
| 产出语义 | 142–144 | 每次全新生成、永不覆写的输出纪律 |
| 反模式表 + 运行原则 | 146–170 | 12 条负面清单 + 5 条总纲 |

下面按模块逐节深讲。

## 2. 元数据头：Skill 的入口协议（第 1–10 行）

### 2.1 是什么

frontmatter 是文件开头两横线之间的一段 YAML 配置。本文件声明了六个字段：

| 字段 | 本文件的值 | 控制什么 |
|---|---|---|
| `name` | `claude-md-draft-for-tech-constrain` | 技能的唯一名字（省略时默认取目录名） |
| `description` | 约 317 字的中文长句 | 触发依据：什么时候该用这个技能 |
| `argument-hint` | `[源文档路径或目录，默认扫描 docs/] [--no-draft]` | 提示用户调用时可以传什么参数 |
| `user-invocable` | `true` | 用户能用斜杠命令手动调用 |
| `disable-model-invocation` | `false` | 模型也能根据描述自动触发 |
| `metadata.version` | `1.1` | 维护者自己记录的版本号 |

### 2.2 为什么这样设计

关键在 `description`。它其实同时写给两类读者：人（在斜杠菜单里看到一句话简介）和模型（AI 靠这段话判断当前对话要不要启用这个技能）。按 Claude Code 官方文档，`description` 是技能被自动触发的判断依据，有 1536 字符上限；本文件只用了 317 字，留足了余量。

更有意思的是它往 `description` 里塞了第三样东西：分流规则。结尾一句写着"按技术栈/代码/会话复盘提炼编程规范、或按现成编程规范文档立规 → 路由 claude-md-draft-for-code-standard"。也就是说，当用户的需求其实是"立代码规范"而不是"从文档提炼导航红线"时，模型在读到描述的那一刻就知道该把活转给姊妹技能。

这是"双轨"设计的一半：仓库里并排放着两个技能，本技能（tech-constrain）从已有设计文档提炼**设计层共识**（架构怎么定、哪些红线不能碰），姊妹技能（claude-md-draft-for-code-standard）从代码与事故证据提炼**编程规范**（代码怎么写、坑怎么避）。两者在各自的说明里互相声明分工——这是把"路由决策"做成显式条款，而不是指望模型临场猜。

### 2.3 怎么用、影响什么

两种用法：在 Claude Code 里输入 `/claude-md-draft-for-tech-constrain docs/design`，或直接说"帮我从这个项目的文档生成 CLAUDE.md"。`user-invocable: true` 加 `disable-model-invocation: false` 的组合意味着人和模型都能发起——代价是描述必须写得足够精准，否则会被误触发。`--no-draft` 参数可以关掉过程产物落盘（见第 4 节）。

## 3. 目标与边界：只产草稿，永不落盘（第 12–22 行）

### 3.1 是什么

目标节（第 14–16 行）把职责压成一句话：把项目已有文档提炼为 CLAUDE.md **草稿**，"产出是供人裁决的草稿，不是生效规则"。随后四条边界（第 18–22 行）划死禁区：

| 边界条款（原文要点） | 禁止的行为 |
|---|---|
| 只从已有权威文档提炼，不发明约定 | 文档里没有的好想法，只能标"文档未明文"，经用户确认才写入 |
| 不修改源文档 | 被提炼的需求/技术方案全程只读 |
| 不写落点 CLAUDE.md | 就算仓库里已有 CLAUDE.md，也只读作对照，绝不直接改它 |
| 检测到 AGENTS.md 等同类载体 → 询问 | 不静默双写，先问"单一权威源+指针"还是两份都维护 |

### 3.2 为什么这样设计

你可能会问：既然目标就是得到一份 CLAUDE.md，为什么非要停在草稿，不直接写好？

因为"写规则"和"生效"是两种性质的权力。AI 提炼的内容可能有错、可能过时、可能和用户手写的心血冲突。CLAUDE.md 一旦生效，其中每句话都会在之后的每次会话里被 AI 当权威执行——一条错误约定会被"代代相传"（这个担忧在反模式表第 4 条里被明确写出）。所以本技能把这两步拆开：机器负责提炼和起草，人负责裁决和拷入。反模式表第 12 条甚至写了"即使用户口头催促"也不把草稿直接写进落点文件，用户真要合并时必须明确二次确认——把 human-in-the-loop（人在环节中把关）做成硬约束，而不是口头建议。

"不静默双写"这条同理：有些项目同时认 CLAUDE.md 和 AGENTS.md 两种说明书。如果 AI 擅自两边都写，同一规则就有了两个维护点，改一处忘一处必然漂移。所以先问清"单一权威源+指针"（一份为主，另一份只放一行指向它的链接）还是双写。

### 3.3 怎么用、影响什么

这条设计直接决定了产物的形态：草稿文件首行是 blockquote 草稿声明（写明生成日期、来源文档集、"是否拷入由用户裁决"），生成内容包在 `<!-- generated START -->` 与 `<!-- generated END -->` 标记区里（第 97–98 行）——标示哪些是机器写的，方便人合并时区分，也保护既有文件里的手写段落不被静默吞掉。

## 4. 输出契约：三个占位符管住 AI 的文件系统行为（第 24–41 行）

### 4.1 是什么

产物落盘路径是一个模板（第 29 行）：

```text
./{OUTPUT_DIR}/consolidate/{YYYYMMDD}_claudemd_draft_{name}.md
```

三个占位符各有规则：`{OUTPUT_DIR}` 是输出根目录（用户未指定默认 `chat`，是本技能唯一的写盘范围）；`{YYYYMMDD}` 是运行日期；`{name}` 是按公式生成的项目标识——"主框架-语言或形态-仓库角色"三段式，比如 `springboot-java-monolith`（Spring Boot-Java-单体应用），小写字母加连字符，不超过 32 字符。

### 4.2 为什么这样设计

第一个细节：日期必须执行 `date +%Y%m%d` 取自系统时钟，原文写"禁止模型凭记忆写"（第 33 行）。这不是较真——语言模型没有可靠的"今天"，训练截止之后的时间全靠会话上下文里的提示，凭印象写日期是高频事故。把"去问时钟"写成指令，是用最便宜的代价消除一整类错误。

第二个细节是撞名处理。你可能会问：如果目标文件已经存在，为什么不直接覆盖？本技能的选择是永不覆盖：撞名检查针对完整文件名（日期+名字整体），撞了就给 `{name}` 追加序号 `-2`、`-3`，重查直到唯一（第 35–36 行）；序号越界就把 `{name}` 压缩腾位、预留序号位（第 37 行）；连撞 5 次才停下来问用户改名（第 39 行）。这是把输出做成"只增不改"的日志式语义：每次运行都是一次独立快照，历史产物永远完好。对比一下"覆盖写"的世界——你跑两次技能，第一次的草稿没了，想对比都无从谈起。

第三个细节是 `{name}` 的截断顺序也写死了：超 32 字符先截"仓库角色"段、按连字符边界截。连字符不连用、不出现在首尾这类排版规则也一并规定。看起来琐碎，但省掉的每一次"模型自由发挥"，都是一次不可预测的产物命名。

### 4.3 怎么用、影响什么

这些规则保证了一个实用性质：同一天跑多少次、多少个项目并行，产物互不覆写（第 41 行）。过程产物（候选笔记）默认落在 `{OUTPUT_DIR}/draft/{YYYYMMDD}_claudemd_draft_{name}/`，`--no-draft` 可关。唯一的写盘根被限定在 `{OUTPUT_DIR}` 子树内，源文档和落点 CLAUDE.md 在文件系统层面就碰不到。

## 5. 不变量与默认值：把编辑经验写成判据（第 43–54 行）

### 5.1 是什么

"不变量"节（第 43–50 行）列出六条任何项目都必须遵守的判据。这是全文的技术核心，值得逐条看：

| 不变量 | 原文要点 | 它防的是什么 |
|---|---|---|
| 1 选材三标准 | 高杠杆（AI 真的会犯、代价大）、稳定（项目任何阶段都为真）、精炼（能一行不两行） | 把文档里什么都往说明书里塞 |
| 2 分层定位 | CLAUDE.md 只答"什么不能做"；任务清单、周计划等"现在做什么"一律排除 | 时效内容过期后变成每次会话的持续噪音 |
| 3 红线写法 | 结论+后果+出处；对权威来源声明从属（"冲突时以 X 为准"） | 无出处的规则无法溯源，多源规则打架无仲裁 |
| 4 五条去重判据 | 位置机制、工具机制、权威文件、受管理区块、时效 | 与目录级文件、工作流工具、宪章类文件重复维护 |
| 5 排除项表 | "考虑过但排除的内容+理由"是一等公民输出 | 排除决策不可追溯，后人重新踩坑 |
| 6 必问与保护 | 固定 5 项必问；手写内容保护；generated 标记区 | AI 越权替人做关键决策、吞掉手写内容 |

### 5.2 为什么这样设计

不变量 3 里的"仲裁句"是最值得展开的一笔。传统做法是承诺"多处文档同步维护"——实践里必败，因为双份维护天然漂移。本技能的替代方案是给每条压缩复述的规则挂一句从属声明："冲突时以 X 为准"。这样哪怕复述版过时了，仲裁句也会把裁决权交回权威源，不需要任何人记得同步。本仓库自己的 CLAUDE.md 里就有现成实例：非协商原则一节标题写着" constitution.md 的压缩复述，冲突时以 constitution.md 为准"。

不变量 2 有一处反直觉的严格：连"当前任务信息去哪看"这种**指针**都不许放（第 46 行）。你可能会问：指针又不会过期，为什么也删？答案是会——"活信息的源随项目阶段漂移"，两周后任务清单从 Notion 挪到 issues，这行指针就变成一个失效地址，而且因为它顶着"权威声明"的名头，AI 会一直信它。修法不是换指向，而是整行删除。

### 5.3 默认值与狗粮观察

默认值节（第 52–54 行）给出可偏离的基线：正文不超过 110 行、3500 字符；目录级拆分文件不超过 2 个；偏离须在候选笔记里写明理由。这个数字的背景是上下文预算：CLAUDE.md 每次会话都会整份注入，占的是 AI 的"工作记忆"，行数就是成本。11 条反模式里的第 1 条（枚举本体必过期，只放"清单见 X"指针）也是同一逻辑的延伸。

顺带一个可实测的对照：本仓库根目录的 CLAUDE.md 实测 74 行、3282 字符，在默认预算内；它的章节（仓库地图、非协商原则、架构关键事实、实施工作流）与第 6 节将讲到的输出骨架逐节对应，实施工作流一节正是"一行存在性指针"的写法。是否由本技能生成，从代码无法考证，但至少说明骨架与实例同源。

## 6. 六步执行流程：一条带质检环节的流水线（第 58–129 行）

### 6.1 第 1–2 步：盘点准入与文档地图

第 1 步（第 60–66 行）做三件事。其一，角色映射：确认文档集里谁是需求权威、谁是技术权威、谁是流程权威、谁是背景——并且明确"不按文档形态要求"，四件套、一堆 ADR（架构决策记录）、甚至单份 README 都行，角色缺位就注明缺位。其二，探测项目自带的工作流体系（`.specify/`、`.cursor/`、Makefile 目标等），探到就触发不变量 4 的让位规则——工具自带的流程约束调用时会自动注入，说明书里复述等于双份维护。其三，准入判定：没有权威文档就停下来建议先补文档；文档间有重大冲突就建议先做评审。这一步的取向是"输入不合格宁可不干"，而不是硬着头皮产出低质量草稿。

第 2 步（第 68–70 行）建文档地图：每份文档的章节清单、引用关系、每类信息的权威源、冲突时听谁的。后续所有"出处"标注都靠这张地图。

### 6.2 第 3 步：选材起草与位置决策

第 3 步（第 72–80 行）按不变量筛选并起草候选笔记，笔记结构固定为"分节正文（附入选理由+逐条来源）→ 排除项表 → 体量评估 → 分层放置说明 → 需拍板项清单"。

其中最有味道的是一条自问式判据（第 80 行）：判断一条规则放根级还是放子目录级文件，问"能否构造一个 agent 全程不在该目录工作、但仍会违反这条规则的场景？"能，就放根级写成自含式一行；不能，就只放到目录级。这把一个容易凭感觉的布局问题转成了可执行的测试。同一段还有个成本意识很强的细节：最高危红线（如宪章保护类）无论判定结果如何，都在根级保留一份自含式副本，注明约 25 token——用极小的预算给最要紧的规则上双保险，防止"目标目录没被打开时规则等于不存在"。

### 6.3 第 4 步：三视角自查——给 AI 的产出也配 code review

第 4 步（第 82–92 行）是整条流水线的质检环节，用一个三列表格规定了三个审查视角：

| 视角 | 检查法 | 执行方式 |
|---|---|---|
| 事实核查 | 逐条候选 grep 源文档，取原文逐字比对 | 始终机械化，主 agent 执行（grep 天然去偏差） |
| AI 执行杠杆 | 纠偏清单逐项在候选中找承接 | 至少与下一视角之一走 fresh-context subagent |
| 取舍合理性 | 逐条排除项反问"指针够用吗" | 同上——起草者不得同时扮演这两个视角 |

这里有个概念值得小栏讲清：fresh-context subagent（全新上下文的子代理）。Claude Code 允许把子任务交给一个"没读过当前对话"的独立 AI 实例执行。为什么自查要用它？因为同一个上下文里的 AI 会顺着自己刚写的思路走——它刚论证过某条该入选，再让它审查就容易自证。换一个只拿到候选清单、不知道起草过程的新实例来审，才接近人类"独立评审"的去偏差效果。事实核查则相反，刻意留在主 agent 用 grep 做：机械比对没有立场问题，还省开销。

配套还有两条纪律。降级条款（第 90 行）：只有全部视角都能机械化、且文档极小时，才允许主 agent 顺序自查，且汇报必须标注"单上下文自查，未经独立复核"——质量等级不许隐瞒。提问上限（第 92 行）：自查产生的待决项合并进第二轮提问，全程最多两轮 AskUserQuestion——把"问人"的成本也纳入预算，防止流程变成连环问卷。

### 6.4 第 5–6 步：生成与汇报

第 5 步（第 94–119 行）按固定骨架生成草稿。必选节四样：草稿声明、一句话定位+范围红线、仓库地图（导航+仲裁规则+快查指针）、非协商原则（权威来源忠实压缩+仲裁句+补充红线）。另有四个菜单节按条件取用：架构关键事实（存在"不知道就会写错方向"的结构性事实时）、实施工作流（项目无自带工作流机制时才展开）、构建与验证、阅读注记。形态规则收口：条目一律单行列表加行末来源，不用多列表格——反模式 10 给了理由：表格易碎，单行列表消费效率最高。

第 6 步（第 121–128 行）汇报，第一项必须是产出文件的完整路径，让使用者直接找到文件；体量汇报用 `wc -l`/`wc -m` 实测行数字符数，原文特意写"不报 token 数"——token 数没法机器实测，行数字节可以。这条细节和运行原则一节（第 168 行）"可机械执行的优先：grep/wc 实测，不凭印象"是同一价值观：凡可验证的，不靠模型自评。

## 7. 人机边界与负面清单：必问清单、产出语义、反模式表（第 132–170 行）

### 7.1 必问清单：什么必须问人，什么 AI 自己定

固定 5 项，"不自行增减"（第 134–138 行）：无出处的新约定是否写入；根/目录归属拿不准的条目；与既有 CLAUDE.md 冲突条目的处置；撞名 5 次仍无可用名时请用户改名；同类载体（AGENTS.md 等）单源还是双写。紧接着一行（第 140 行）把剩余决策全部划给 AI："其余（选材、压缩、措辞）自行决定，汇报中说明理由。"

这张清单的筛选逻辑值得学：列入的都是**后果不可逆或涉及用户意图**的事（动用户的文件、替项目发明规则），划出的是**可逆且可解释**的事（措辞、取舍）。配套的提问上限（全程两轮）进一步压住了打扰成本。

### 7.2 产出语义：全新生成，永不覆写

第 142–144 行单独成节，还带着一个内嵌修订日期"（2026-09-03 更新）"——文件自身演进留下的痕迹。内容是把输出纪律说绝：每次运行全新生成，不读取、不比对、不增量补写既有草稿；落盘前按撞名规则重查完整 token；"永不覆写既有文件，也不问覆盖"；新旧草稿怎么取舍由使用方裁决。它和第 4 节的占位符规则互为表里：那里定义"落到哪个唯一路径"，这里定义"到了路径也不许改已有东西"。

### 7.3 反模式表：12 条负面清单为什么有效

第 146–162 行是一张 12 行的反模式表，每行"反模式+原因"。挑五条看其锋利程度：

| # | 反模式 | 原因（原文压缩） |
|---|---|---|
| 1 | 把端点/命令/配置清单抄进 CLAUDE.md | 必过期，只放"清单见 X"指针 |
| 3b | 连"当前活信息在哪"的声明都放 | 源随阶段漂移，删除而非换指向 |
| 5 | 用纯指针替代自含式关键规则 | 触发场景不在目标目录时等于没有 |
| 9 | 用 @path 把目录级文件导入根文件 | 无条件加载破坏按需注入的惰性分流 |
| 12 | 把草稿直接写进落点 CLAUDE.md（即使用户口头催促） | 拷入是用户裁决动作 |

第 5 条与第 3 步的位置决策判据、第 1 条与不变量 1 的"稳定"标准、第 12 条与第 3 节的草稿语义——负面清单不是新规则，而是把前面各节的正向设计以"禁止"的形式再钉一遍。这正是负面清单的价值：正向条款告诉 AI 该做什么，负面条款封死它最可能滑进去的捷径，两条路夹住，行为才稳定。

### 7.4 运行原则：五条总纲

末节（第 164–170 行）收束为五条：只读源文档与既有 CLAUDE.md、永不写落点；证据优先（每条候选附来源、每条排除附理由）；可机械执行的优先（grep/wc 实测不凭印象）；不确定必问；全新生成。它们是前七节内容的公因式——如果只允许记住一节，记住这节也能还原大半个技能。

## 8. 收尾：学到什么、怎么迁移

回头看，这份 170 行的文件示范了五件可迁移的事：

1. **提示词当程序写**：配置（frontmatter）与逻辑（正文）分离；章节即模块；判据写成可执行的条件（"能否构造 agent 不在该目录仍违反的场景"），不写成感觉性的形容词。
2. **把人的裁决点做成硬约束**：产物是草稿、拷入归用户、"口头催促也不写落点"——涉及不可逆后果的权力不交给自动化。
3. **输出不可变化**：占位符保证路径唯一，撞名加序号永不覆盖，历史快照永远可考。
4. **给 AI 的产出配独立质检**：机械比对用工具（grep/wc），判断类审查换 fresh-context 实例，质量等级如实汇报。
5. **负向条款钉死捷径**：12 条反模式把正向设计的漏洞逐条封上，并给出每条的原因。

迁移到任何"让 AI 按规程干活"的场景都成立：写部署 SOP、定代码评审流程、做数据清洗管道提示词，都可以套用这套骨架——入口协议、禁区边界、输出契约、质量判据、带质检的流程、必问清单、负面清单。唯一要提醒的：这文件里的规则本身也遵守它教的道理——精炼、稳定、有出处、不含时限内容。写规则的经验和被写的规则，在这里咬合成了一个闭环。
