# 给 AI 立规矩，给自己讲明白：一份 VitePress 站点规范精读

## 1. 开篇：一个官网，和一份写给 AI 的说明书

先说这个网站是什么。仓库 `website/` 目录下有一个官网项目，用的是 **VitePress**——一个「静态站点生成器」。这个名字听起来唬人，拆开很简单：你写 Markdown 和少量组件，它帮你编译成一堆纯静态的 HTML、CSS、JS 文件，扔到服务器上就能访问。没有后端、没有数据库，访问者拿到的是早就生成好的页面，所以又快又稳。

这个站点本身很小：一个双语文案的主页（英文版和中文版），加上一些图标、字体和架构图。全部源码数得过来：一份站点配置、一个常量文件、两个 Vue 组件、一份全局样式、两个 Markdown 首页、一个 [Makefile](https://github.com/fangkun119/agent-os-poc/commit/6c168a748da3c537c9231717385cfe4ad36d7e99/website/Makefile)、一个 [package.json](https://github.com/fangkun119/agent-os-poc/commit/6c168a748da3c537c9231717385cfe4ad36d7e99/website/package.json)。

但目录里还有一份特殊的文件：[CLAUDE.md](https://github.com/fangkun119/agent-os-poc/commit/6c168a748da3c537c9231717385cfe4ad36d7e99/website/CLAUDE.md)。它不是给人看的入门文档，是写给 AI 编程助手（Claude Code 这类工具）看的「站点规范」。AI 改代码前会先读它，把里面的约束当作硬性纪律。

为什么 AI 时代需要这种文件？因为 AI 写代码有两个特点：不知道你项目的「家规」，而且执行力极强——你不说清楚，它就按自己训练数据里的通用习惯来，可能一口气引入外部 CDN、把字段名臆造一通、顺手把主题覆盖写错地方。人 Review 能兜住一部分，但最好的办法是把坑提前写成规则，让 AI 在动手前就知道红线在哪。

这份 CLAUDE.md 就是这么一份「踩坑说明书」。它分六章加一组速记约定：通用工程纪律、构建与验证、站点配置与常量、Vue 组件、样式与主题、文档内容、速记约定。本文按它的章节顺序逐条精读，每条讲三件事：它防的是什么事故、它的机制原理、以及在真实代码里对应哪段证据。

开篇先交代两处不展开的内容：文件头尾有两段 HTML 注释形式的「维护者注」，一段说明这份文件本身是个可复用模板（拷到新项目、按文末「站点参数清单」逐项替换即可），另一段是「勿再加清单」（曾经论证后被否决的规则，防止后人重新提出来）。这两处是给维护文件的人看的元信息，不是站点代码规范，本文不逐条展开。

## 2. 通用工程纪律：改代码先管住手

这一章的四条规则和具体技术无关，管的是「改代码这个动作本身」。放在最前面，因为 AI 最容易犯的恰恰不是技术错，而是「手伸得太长」。

### 2.1 外科手术式改动 + 清理自己产生的垃圾：改动范围的纪律

这两条是一对，防的是同一个病：改动失控。

「外科手术式改动」防的画面是这样的：你让 AI 加一个按钮，它顺手看到旁边有个函数命名不顺眼，重构了；重构时又发现一处重复代码，抽了个公共类。半小时后 Diff 有两百行，你根本没法确认「我要的那个按钮」到底对不对——review 成本直接爆炸。

对应的约束原文：「改动都应能对应到本次需求；与需求无关的代码不顺手重构、不顺手清理」，发现的存量问题「梳理并给出修改建议，排出优先级，交给开发者决定」。翻译成大白话：发现问题可以提，但手别动，决定权在人。

「清理自己产生的垃圾」防的是另一半事故：删了某个数据数组，却把数组对应的样式、引用留在原地，成了没人敢动的「孤儿代码」。约束是「自己改动产生的孤儿必须清干净；既有存量问题只指出、不擅自删改」。

你可能会问：这两条在代码里怎么验证？它们的证据形态不是某一行代码，而是一种「痕迹」——目录里四份核心文件的头部注释，都明确标注了自己服从 CLAUDE.md 哪一条纪律。[Home.vue](https://github.com/fangkun119/agent-os-poc/commit/6c168a748da3c537c9231717385cfe4ad36d7e99/website/.vitepress/theme/components/Home.vue) 开头列了「文案一律 t(zh, en)」「模板字符串内 shell 变量必须写成 \${VAR}」等约定；[custom.css](https://github.com/fangkun119/agent-os-poc/commit/6c168a748da3c537c9231717385cfe4ad36d7e99/website/.vitepress/theme/custom.css) 头部写着「主题覆盖只写本文件；.VP* 内部类用最窄选择器并注明压的是哪条内部规则」。改代码的人（或 AI）把规范抄在自己头顶，等于每改一行都有对照清单。同时整个样式表里找不到一条「定义了却没人消费」的变量、组件里找不到一段「渲染了却没人要」的残留节点——孤儿清理是做到位的状态。

### 2.2 代码注释：陈述事实，不讲故事

这条防的事故：注释变成「变更日志」。比如「这里原来用 A 方案，后来不再使用，改成 B」。这种注释三个月后就是毒药——读者不知道「原来」是多久以前、A 方案还在不在，代码和注释互相打架。

规范给了三个硬标准：

1. 「禁止叙事变更历史（now/previously/原来/不再…）」——注释只写此刻的事实，不写怎么走到这一步的。
2. 「注释必须陈述代码本身读不出的信息，否则不写」——代码能看懂的，注释重复一遍就是噪音。
3. 「workaround 类注释注明成因与出处」——绕坑的代码必须说清绕的是什么坑、坑的出处在哪。

实际代码是这套标准的高分样本。[config.mts](https://github.com/fangkun119/agent-os-poc/commit/6c168a748da3c537c9231717385cfe4ad36d7e99/website/.vitepress/config.mts) 里每一处「看起来像 bug 的写法」都有注释讲清为什么：

```ts
// 有意设置：nav 只留 logo，站名经 logo 承载（勿当缺陷修复补回文字）
siteTitle: false,
```

导航栏上只放 logo 不放站名，正常人都会以为是漏了。这行注释一句话封死了后续所有「好心修复」。再看 sitemap 那行：「hostname 需自带 base（含尾斜杠）：vitepress 1.6.4 generateSitemap 只拼 hostname + 页面相对路径，不加 base 且缺尾斜杠会多一次 301」——连具体版本号和后果都写了，这是典型的「代码读不出的信息」。全目录注释里没有一处「原来」「不再」式叙事。

### 2.3 挂起决策不擅自落地：别替人做决定

这条防的是：项目里标了「待决策」的问题，AI 看着难受，默默选了个方案写进代码。等真正的决策做出来，发现代码已经往另一个方向跑了，返工。

约束是「呈现选项而非默默选边；未决期间相关条款不得写出互相矛盾的表述」。当前代码里没有「待决策」标记——色板 v3 已定稿（`custom.css` 头注释指向定稿记录），没有挂起项。所以这条在目录里没有直接证据对象，属于「备用纪律」：它约束的是出现开放问题那一刻的行为，本文按原文如实转述，不编造事故现场。

### 2.4 零运行时外部请求：私有部署的硬约束

这条是整个站点的「物理定律」，防的事故很具体：访客打开你的页面，浏览器向第三方 CDN 发请求去取字体、图标——公司内网部署时这些域名全被防火墙拦掉，页面字体全丢、图标空白，还把访客 IP 泄露给了第三方。

规范的解法分三层。第一层，「字体、图标、图片一律站内自托管或内联」。证据非常整齐：字体文件 `inter-latin-var.woff2` 和 `jetbrains-mono-latin-var.woff2` 就放在站点自己的 `public/fonts/` 目录，由 `custom.css` 里的 `@font-face` 规则声明加载——**@font-face** 是 CSS 里「告诉浏览器去哪下载这个字体」的声明，这里下载地址指向站内。还有一个细节很讲究：`unicode-range` 把这份字体限定在拉丁字符范围，中文字符落回系统自带的苹方/雅黑，中文大字的个性由字重承担。注释写明这是有意取舍，避免为中文再背一份几 MB 的字体文件。

图标同样内联。Home.vue 里 GitHub 图标、按钮箭头都是直接写在模板里的 `<svg>` 代码，不引用任何图标 CDN；导航栏的 GitHub 图标用的是 VitePress 内置的 SVG，也不出网。规范特别点名「不用 iconify 类字符串图标名」——那类方案在代码里只写一个图标名字符串，浏览器运行时才去图标 CDN 拉取，正好踩中零外部请求的红线。

第二层，「新增外部 origin 先向用户提出并获确认」。第三层是条件降级：如果站点改走公有网部署，这条放松为「运行时外链需显式豁免」。这是维护者注里「站点参数清单」的一项——同一份模板，部署形态变了，规则跟着变。

## 3. 构建与验证：make 单一入口

先补一个概念：**构建**（build）就是把 Markdown 和组件「编译」成浏览器能直接打开的静态文件的过程，产物默认落在 `.vitepress/dist/` 目录。这一章管的就是「怎么构建、怎么确认构建结果是对的」。

### 3.1 make 单一入口与验证定义

这条防的事故：文档里一会儿写 `npm run build`，一会儿写 `npx vitepress build`，一会儿又让你先删缓存。AI 挑一个执行，跑出来的行为和你预期的不一致。

解法：所有操作收口到一个入口。规则原文「构建/预览一律走 make 目标」，并且新增 npm script 时必须「同步补 make 目标 + `##` 开头的用途注释 + `.PHONY` 声明」。三个配件各有用途：`##` 注释让 `make help` 类场景能看到用途说明；**.PHONY** 声明告诉 make「这个名字不是文件」——不声明的话，如果目录里恰好有个叫 `build` 的文件，`make build` 会认为「文件已存在，无需执行」而直接跳过，这是 make 的经典暗坑。

你可能会问：为什么不直接用 `npm run`？看 [Makefile](https://github.com/fangkun119/agent-os-poc/commit/6c168a748da3c537c9231717385cfe4ad36d7e99/website/Makefile) 就明白了——make 目标可以串联多条命令。`build` 目标执行了两步：`npm run build` 之后 `touch .vitepress/dist/.nojekyll`。这行是点睛之笔：GitHub Pages 默认用 Jekyll 渲染，会忽略下划线开头的资源路径，导致整站 404；`.nojekyll` 这个空文件就是开关，但构建工具不会拷贝 `public/` 里的点文件，所以必须构建后手动补一个。这种「npm script 表达不了的多步编排」，正是 make 入口的价值。而 [package.json](https://github.com/fangkun119/agent-os-poc/commit/6c168a748da3c537c9231717385cfe4ad36d7e99/website/package.json) 里的 scripts 反而极简，只有 dev/build/preview 三个直通命令。

「验证定义」条接着把「做完」的标准钉死：`make build` 退出码 0（**退出码**是命令结束时报告给系统的数字，0 表示成功）+ `make preview` 打开预览页人工目检。为什么目检不能省？因为下一章会讲到，VitePress 有大量「静默失效」的配置——不报错、也不生效，只有眼睛能看到。这个站点没有测试套件，这两步就是唯一的完成标准。

### 3.2 指令文件命令红线 + 禁裸静态服务器：两类「假验证」

两条规则合成一组，防的都是「验证本身是假的」。

第一条防的事故：README 或规范里写了 `make clean`、`rm -rf` 之类的命令，AI 把指令文件里的命令当作「可以自动执行的操作清单」，在一次例行操作里顺手清了库。规范的原话很清楚：「写进指令文件的命令会被 agent 当作可自动执行项；禁止写入 make clean 及任何 rm/覆盖类破坏性命令」。证据在 Makefile 第二行注释：「以下命令均可安全重复执行，无 clean/rm 类破坏性目标」——install、dev、build、preview 四个目标，重复跑一万次都不会破坏现场。注意 `build` 也不做清空重来的动作，代价是要求开发者自己保证产物新鲜，换取的是绝对安全。

第二条防的是更隐蔽的「假预览」。这个站点开了 `cleanUrls: true`——产物 URL 不带 `.html` 扩展名，`/about` 这种地址由 `about.html` 文件提供。你用任意的通用静态服务器（比如 `python -m http.server`）去伺服产物目录，它遇到 `/about` 会去找 `about` 这个文件或目录，找不到就 404。规则一句话点破：「假预览等于假验证，预览只用 make preview」——`vitepress preview` 自带的服务器认识这种映射。Makefile 的 preview 目标注释里也重复了这句警告，规范和构建脚本互相提醒。

## 4. 站点配置与常量（.vitepress/）

这是全文最重的一章，十条规则里有八条在防同一类事故：**静默失效**——配置写错了层级、写错了字段，VitePress 不报错，只是不照做。页面照常构建，问题上线了才被人眼看见。

### 4.1 双语范围：哪些要两份，哪些只要一份

这个站点是双语的：英文站挂在根路径，中文站挂在 `/zh/` 子路径。规范第一条就要求动手前先分类——「新增内容先判断属于哪一侧」。

需要中英两份的，是「面向访客」的内容：页面文案、导航标签、文档页、分享到社交网络时的摘要信息。保持单语的，是「不需要翻译」的内容：代码示例、代码注释、站内收录的外部文档镜像、维护者文档。

看 Home.vue 的数据就懂这条线的价值。页面标题、按钮文字、卡片描述全部双语成对；但每张能力卡片里的 `code` 字段——那些终端命令和 YAML 配置示例——只有英文一份。代码是给开发者看的，翻译它只会制造错误信息。

还有一个精妙的中间态：常量文件里的副标语。[constants.ts](https://github.com/fangkun119/agent-os-poc/commit/6c168a748da3c537c9231717385cfe4ad36d7e99/website/.vitepress/constants.ts) 里 `TAGLINE_EN` 和 `TAGLINE_ZH` 是一对常量，注释写明「双语成对」——它们是访客可见文案，所以要双语；但它们定义在单语维护的常量文件里，英文版只是「值」，不是「需要维护的第二份文档」。这个分类法（按受众分类，不按文件分类）就是这条规范想教给 AI 的判断力。

### 4.2 双语三处同步：成对落地，数量相等

分类定了之后，落地时有个纪律：「文档页 en/zh 成对落地（docs/x.md ↔ zh/docs/x.md 同名 1:1），同一提交里同步 root 与 zh 两份 nav/sidebar」。防的事故是「只加了一侧」：英文导航加了新页面，中文侧忘了——VitePress 对此不报任何错，中文访客点过去就是线上 404。

当前证据是这套约束的最小实例：config.mts 里英文侧 `nav` 有一项 `{ text: 'Home', link: '/' }`，中文侧有 `{ text: '首页', link: '/zh/' }`，两侧数量相等、一一对应。至于文档页本身——如实说明：站点目前只有双首页，`docs/` 和 `zh/docs/` 目录还不存在（文档站属于路线图第三阶段），这条纪律的完整形态要等文档页诞生后才有完整证据。规范提前立在这里，正是为了防「文档页开写时忘了配对」。

### 4.3 locale 级配置九键：写错层级就静默失效

先补概念：VitePress 的配置文件 config.mts 导出一个配置对象，其中 `locales` 字段下分 `root`（英文站）和 `zh`（中文站）两个 **locale**（语言分区），每个分区可以有自己的标题、描述、导航等。

这条规范划了一条清晰的线：「locale 级只允许九键」——七个基础键（`lang`/`dir`/`title`/`titleTemplate`/`description`/`head`/`themeConfig`）加语言切换器的 `label`（必填）和 `link`（可选）。防的事故：把 `base`、`cleanUrls` 这类**站点级**键（整个站点只该有一份的配置）误写进某个 locale 分区——VitePress 不会报错，只是忽略它。想象一下：你把「站点部署在子路径」的配置写进了中文分区，英文站行为不变、中文站也不变，你以为配置生效了，部署上线才发现全错。

你可能会问：写错了为什么不报错？因为 locale 对象在 VitePress 内部就是「它认识哪个键就读哪个」，多出来的键只是躺在对象里没人看。这就是静默失效的本质——类型上不报错、运行上无感知。

对照代码：[index.md](https://github.com/fangkun119/agent-os-poc/commit/6c168a748da3c537c9231717385cfe4ad36d7e99/website/index.md) 与 [zh/index.md](https://github.com/fangkun119/agent-os-poc/commit/6c168a748da3c537c9231717385cfe4ad36d7e99/website/zh/index.md) 两个首页文件的 frontmatter（Markdown 文件头部的元数据区）先按下不表，config.mts 的 locale 分区里只出现 `label`、`lang`、`link`、`description`、`head`、`themeConfig`，全部在九键清单内；`base`、`cleanUrls`、`appearance`、`srcExclude`、`sitemap` 这些站点级键全部写在顶层。层级纪律执行得一丝不苟。

九键之外还有两个细则。其一，「themeConfig 为浅合并」——**浅合并**是指 locale 层和站点层的 themeConfig 合并时只比一层：你在中文 locale 的 themeConfig 里写了个数组（比如导航），它不会和英文侧的数组合并，而是整个换掉。所以规范要求「nav/sidebar 两侧各写全量、勿写增量」——每侧都写完整清单，别指望继承。其二，「不建目录级 config 覆盖文件，保持单一配置源」，配置只活在 config.mts 一个文件里。

配套的还有一条「nav/sidebar 字段纪律」：字段名必须以所用版本 VitePress 的类型定义（`DefaultTheme.NavItem`/`SidebarItem`）为准，「禁臆造字段（icon/badge/description 等会被静默丢弃）」。AI 很爱给导航项加 `icon` 字段——官方文档某些版本的类型里没有它，写了就是悄悄消失。验证方法也在这套规范里被反复使用：对着安装的版本查源码。我在阅读时验证了一个实际案例——两个首页 frontmatter 里的 `markdownStyles: false` 这个键名在通用文档里少见，我在本地安装的 vitepress 1.6.4 源码里 grep 到 `VPHome.vue` 中确实有 `frontmatter.markdownStyles !== false` 的判断，确认是真实生效的键。「以所用版本源码为准」不只是规矩，是可操作的工作方法。

### 4.4 默认主题文案本地化：源码里看不见的英文

这条防的事故很刁钻：站点中文页面上，「上一页/下一页」「本页目录」「回到顶部」这些按钮全是英文。因为 VitePress 默认主题的界面文案是**硬编码在主题源码里**的英文——你的项目代码里搜不到它们，改无可改。

解法是在 locale 级 themeConfig 里显式覆盖。config.mts 中文分区里整整五项：`docFooter`（上一篇/下一篇）、`outline.label`（本页目录）、`sidebarMenuLabel`（目录）、`returnToTopLabel`（回到顶部）、`langMenuLabel`（切换语言）。注释还补了一句执行纪律：「英文界面源码不可见，只能 build 后到产物页核验」——这正好回扣 3.1 的验证定义：构建通过不算完，要打开产物页用眼睛确认。

### 4.5 public/ 资产引用：withBase 与路径的三种形态

先补概念：**public/ 目录**是静态资产（图片、字体、图标）的「原样拷贝区」，构建时原封不动搬进产物。**base** 是站点的部署前缀——这个站点部署在 GitHub Pages 的子路径上，真实地址是 `fangkun119.github.io/agent-os-poc/`，所以 base 是 `/agent-os-poc/`。

事故现场来了：你在组件里写 `<img src="/images/arch.png">`，本地开发一切正常；部署到子路径后，浏览器去找 `域名/images/arch.png`，而真实位置是 `域名/agent-os-poc/images/arch.png`——图片 404。路径少了前缀。

解法分三种场景，规范各给一条路：

组件内用 `withBase()`。这是 VitePress 提供的函数，自动把 base 前缀拼在路径前面。Home.vue 里的架构图就是这么处理的：

```js
const archImage = computed(() =>
  withBase(isZh.value ? '/images/architecture-zh.svg' : '/images/architecture-en.svg')
)
```

base 变了，这行代码不用动。

config 的 head 和 Markdown 里用根绝对路径（`/favicon.svg` 式）。这里规范原文和实际代码有一处分歧，值得单独说（详见文末设计决策记录第 1 条）：规则写的是 head 里用根绝对路径，但代码里 favicon 的 href 实际写成了 `/agent-os-poc/favicon.svg`——手动带上了 base 前缀，注释解释「head 内根绝对路径 VitePress 不做 base 重写（favicon 在 GitHub Pages 子路径下会 404），故此处唯一例外地硬编码 base 前缀；改 base 时本行同步改」。按「代码为准」原则，真实约束是：**head 里的路径不会被自动补前缀，需要自己带上**。规范原文落后于代码一步。

CSS 里的 `url()` 是第三种形态。custom.css 里字体写的是 `url('/fonts/inter-latin-var.woff2')`，看着也是不带前缀的路径——但我核对过构建产物 `dist/assets/style.css`，里面的地址已经是 `/agent-os-poc/fonts/inter-latin-var.woff2`，说明构建工具对 CSS 内的资产路径做了自动重写。三种场景三种行为：组件内手动 withBase、head 内完全不管、CSS 内构建期自动处理——不理解这个分野，每一处都是上线后的 404。

规范还配了两条护栏：「禁止在 md 里用相对路径爬出 srcDir 指向 public/」——那种写法会让打包器解析失败，构建直接报错挂掉（这是本节唯一「响亮」的失败，反而最好查）；「改 base 时需全局复查根绝对路径与 CSS 内 url() 引用」。base 一变，全站路径都是嫌疑犯。

### 4.6 themeConfig 联动陷阱：四个静默面

themeConfig 是主题配置块，里面有四个「改 A 动 B」的联动陷阱。规范用一张四行清单讲清，每一条都是「静默」级别——这里直接用表格对照代码：

| 陷阱 | 防的事故 | 代码证据 |
| --- | --- | --- |
| `titleTemplate` 的 `:title` 取页面首个 h1 | 改了首页第一行大标题，浏览器标签页标题和分享卡标题跟着变 | 两个首页 frontmatter 里显式写了 `titleTemplate: false`，注释「首页 frontmatter 标题已含站名，关掉站点级 titleTemplate 后缀防品牌叠加」——站点级模板是 `:title — ${SITE_NAME}`，首页标题里已经有站名，再套一层就是「AgentOS — AgentOS」 |
| `siteTitle: false` 是有意设置 | 后来者以为站名丢失是缺陷，好心「修复」成 logo+文字双品牌 | config.mts 注释「有意设置：nav 只留 logo，站名经 logo 承载（勿当缺陷修复补回文字）」 |
| 单主题站点的 logo 禁写 light/dark 双值 | 站点根本不区分深浅色，双值是永远走不到的死分支 | `logo: { src: '/logo.svg', alt: SITE_NAME }` 单值形态，且注释提醒「alt 空则链接无可达名」 |
| footer 只在无 sidebar 的页面渲染 | 配了 `themeConfig.footer` 以为有页脚，有侧边栏的页面悄悄没有 | 该站未配 footer，页脚由 Home.vue 自绘；custom.css 里干脆把主题默认页脚隐藏了，注释「压 .VPFooter 的默认渲染以防未来误配 footer 时出现双页脚」 |

这一节的共同教训：主题配置项之间不是独立的，改一个可能牵动另一个，而且牵动过程不报错。唯一可靠的防御是「每个反直觉的配置都留一行『这是有意的』注释」——这个站点做到了。

### 4.7 站点常量单一来源：constants.ts

站名、仓库地址、部署根地址、双语副标语——这些字符串在 config.mts 和 Home.vue 里都要用。防的事故：改站名时改了配置忘了组件，页面上同时存在新旧两个名字。

解法是「站点常量单一来源」：[constants.ts](https://github.com/fangkun119/agent-os-poc/commit/6c168a748da3c537c9231717385cfe4ad36d7e99/website/.vitepress/constants.ts) 一个文件集中定义，「一律 import 使用，禁止在使用处写死字面量」。config.mts 从它 import `SITE_NAME`、`REPO_URL`，Home.vue 也从它 import——两个消费方共用一个真相。

这个文件还有一条容易忽略的硬规矩：「保持零依赖（不 import vitepress/Node 内置/npm 包）」。为什么？因为它同时被两个世界引用：config.mts 在 **Node 侧**（构建机的 Node.js 进程里）执行；Home.vue 会被打包进**浏览器侧**产物，在访客浏览器里执行。一旦 constants.ts 引了 Node 专属的包，浏览器打包直接失败；引了浏览器专属的东西，Node 侧构建又炸。零依赖是让一份文件安全穿越两个世界的唯一办法。规范还留了出口：「确需依赖的共享逻辑另建模块，并在文件头注明适用侧」。

但单一来源有个天然例外：Markdown 文件的 frontmatter（文件头部的元数据区）没法写 import。两个首页 frontmatter 里的分享链接 `https://fangkun119.github.io/agent-os-poc/` 只能手写。规范没有装作能解决，而是老实标注「属人工同步副本，改动时对照同改」——承认弱点，规定动作。

### 4.8 两条留观条目：站内链接扩展名与死链豁免

两条规则在当前站点证据薄弱，成组略讲，交代清楚现状：

「站内链接扩展名」条：站内导航和普通页链接省略 `.md`/`.html` 扩展名（当前证据就是 nav 里的 `link: '/'` 和 `link: '/zh/'`）；但如果站点收录外部文档镜像，镜像之间的互链要保留 `.md`——这是例外。规范的担忧很超前：「不写明例外，agent 对照官方 best practice 批量『修正』镜像链接就是默认错误动作」。另外「`i18nRouting` 保持默认」——语言切换器按路径前缀跳转（英文页 `/x` 对应中文页 `/zh/x`），改 false 切换器就 404。当前站点无镜像文档、页面互链极少，这条主要防未来。

「死链豁免纪律」条是条件式规则（「若启用 `ignoreDeadLinks`」）。查 config.mts，这个键根本没启用——构建时 VitePress 会检查所有站内链接，站点目前靠默认检查兜底，不需要豁免。所以整条暂时不生效，属于「复制模板到新项目时按需保留」的条款。

## 5. Vue 组件（.vitepress/theme/*.vue）

进入组件章。先补最小概念：**Vue 组件**是前端里「一小块自带结构和行为的界面」的封装单位。一个 `.vue` 文件通常分三块：`<template>`（界面的 HTML 结构）、`<script setup>`（数据和行为逻辑）、`<style scoped>`（只作用于本组件的样式）。Home.vue 就是标准的三块结构：284 行逻辑、258 行模板、680 行样式。

### 5.1 双语机制：t(zh, en) 与 computed

这是全站最核心的一条工程规则。防的事故先讲现象：访客在英文页点了语言切换，地址跳到了中文页，但页面上一半文字还是英文——因为有些文字是在「第一次打开页面」那一刻算好的，之后语言再变它也不跟着变了。

看 Home.vue 开头的实现，三个零件：

```js
const { lang } = useData()
const isZh = computed(() => lang.value === 'zh-CN')
const t = (zh, en) => (isZh.value ? zh : en)
```

`lang` 是当前语言；`isZh` 是「是不是中文」的判断；`t` 是个极简翻译函数——传中文和英文两个值，按当前语言返回一个。全站一百余处文案调用都走它，比如 `t('快速开始', 'Get Started')`。规范要求「zh 在前」，对应「root=en」的目录约定，参数位置本身就是文档。

第二个零件是这条规则真正的牙齿：「随语言变化的数据数组一律包 `computed()` 依赖语言判定，不写普通 const」。这里需要讲清**响应式**：Vue 会追踪数据变化，数据变了自动重新渲染界面。`computed` 是「带追踪的求值」——它依赖的数据一变，它的值自动重算，界面跟着刷新。普通 `const` 没有追踪，语言切换后它还停留在首载那一刻的值。

你可能会问：语言切换不是跳转到另一个页面了吗，组件会重新加载，const 应该也重算吧？这正是这条规则最值钱的地方——不能赌。规范原文说得直白：「组件一旦常驻或被复用，普通 const 会固化首载语言」。VitePress 做语言切换时组件可能被复用而不销毁重建（这正是它切换快的原因），那一刻普通 const 就成了「卡在旧语言里的化石」。代码里连一个不起眼的角落都有意识地遵守了：`docRefs` 函数的注释写着「映射在每次调用时求值（内含 t()，普通 const 会固化首载语言）」。统计数据、能力卡片、场景卡片、路线图、终端演示行——所有含文案的数据数组全部是 `computed(() => [...])`，无一例外。

站内链接同理：「`t('/zh/docs/x', '/docs/x')` 成对书写并包 `withBase()`」——语言不同，链接的路径前缀也不同，链接也是「随语言变化的文案」。

### 5.2 模板字符串转义：build 级红线

先补概念：JS 的**模板字符串**是用反引号（`` ` ``）包起来的字符串，里面可以嵌表达式。关键在于：写 `${...}` 的地方会被当成 JS 表达式**当场求值**。

事故画面：能力卡片要展示一段 YAML 配置示例，里面有 `api-key: ${DEEPSEEK_API_KEY}`。这段示例在 JS 代码里是模板字符串，如果 `$` 前没加反斜杠，构建时 JS 会把 `${DEEPSEEK_API_KEY}` 当作变量去求值——构建机上根本没有这个变量，求值结果不是报错就是变成 `undefined`。规范标它「build 级红线」：构建直接失败。

看真实代码里怎么写（Home.vue providers 卡片）：

```js
code: `# application.yaml — keys via env
providers:
  deepseek:
    api-key: \${DEEPSEEK_API_KEY}`
```

`\${DEEPSEEK_API_KEY}`——反斜杠告诉 JS「这是字面文本，别求值」，页面上访客看到的就是 `${DEEPSEEK_API_KEY}` 原样。规范同时禁止字符串里出现未转义的反引号和代码围栏（反引号会提前终止字符串，同样是构建期爆炸）。

你可能会问：为什么不换个占位写法，绕开转义？因为 `${VAR}` 是 shell 和 YAML 生态里环境变量的通用记法，示例代码的任务是「和读者将来真实写的配置长得一样」。宁可写代码的人多打一个反斜杠，不让读文档的人看到篡改过的示例。

### 5.3 数据驱动段落：改数组不改模板

防的事故叫「两份真相」：同一段内容既写在数据里又写在模板里，改了一处忘了另一处，页面自己跟自己矛盾。

规范的做法：「段落文案与条目只改 script setup 顶部的数据数组，模板只做 v-for 渲染，禁止在 template 里写静态副本」。Home.vue 是教科书级执行：script 顶部从上到下排着 `stats`（五个数字）、`capabilities`（六张能力卡）、`runs`（三个场景）、`personas`（一行人设文案）、`roadmapPhases`（三个阶段）、`heroLines`（终端演示的每一行）、`ctaLines`（快速开始的每条命令）——七个数据数组，页面八个板块的内容全在里面。模板里对应的只有 `<div v-for="cap in capabilities" ...>` 这类循环渲染。想改「9 个内置 Tool」这个数字？只动 `stats` 数组一行，模板一行不用碰。

「新增一个段落 = 数据数组 + section 模板 + scoped 样式三件套」——这句把「加内容」标准化成了固定配方。

两个细则都有实证。其一，「组件内没有 markdown 渲染管线，代码示例只能是纯文本字符串进 pre/code」——`<pre class="cap-code"><code>{{ cap.code }}</code></pre>`，原样显示，没有语法高亮管线可用，想高亮只能手写 span 加类名。其二，「v-for 必带 `:key`」——**key** 是给每个循环项的身份证，Vue 靠它识别「哪一项变了」。字符串 key 还要注意唯一性：卡片用 `:key="cap.entry"`（文件名不重复），而终端演示行因为内容可能重复（连续两个空行），用的是 `:key="i"` 索引——数据特点决定 key 选型。

### 5.4 script setup 形态红线：禁顶层 await

这条防的是全规范里后果最诡异的事故：**页面整页空白，且 dev 和 build 都不报错**。

机制拆开讲。`await` 是 JS 里「等一个异步操作完成」的关键字。如果在 `<script setup>` 顶层直接写 await，Vue 会让这个组件变成「异步组件」——渲染它之前要先等异步完成。而 Vue 等待异步组件的机制叫 **Suspense**（一种「先显示占位、数据到了再渲染」的包裹层）：外层必须有人包一层 Suspense，组件才会被渲染。VitePress 自定义主题的 Layout 通常没包。结果就是：组件永远「等待中」，页面空白，控制台安静如初。

规范的解法一句话：「异步取数走 onMounted」。**onMounted** 是 Vue 的生命周期钩子——组件挂载到页面之后执行的函数，异步逻辑放这里，组件本身保持同步，渲染永不被阻塞。

Home.vue 里的实例正是这样：hero 终端的逐行显现动画，延时的计算和注入全部放在 `onMounted(() => {...})` 里。组件先同步渲染出完整内容，挂载之后再补动画时序。顺带一提，这段代码还顺手检查了 `prefers-reduced-motion`（见 6.5），一石二鸟。

配套的形态约束还有一条：「顶层绑定直接用于模板，禁止 Options API / `setup()` return 写法」——`<script setup>` 是 Vue 3 的推荐形态，顶部的变量和函数直接就能在模板里用，不需要 return。全目录两个组件都是纯 `<script setup>`，无例外。

### 5.5 组件契约：文件名、注册点与 theme-without-fonts

这条规则管的是「组件和外界的三个接缝」，每个接缝都是断了不报错的类型。

接缝一：组件文件名和全局注册点。「theme 入口的 `app.component('Home', …)` 与 md 里的标签字符串」是硬依赖。看 [index.ts](https://github.com/fangkun119/agent-os-poc/commit/6c168a748da3c537c9231717385cfe4ad36d7e99/website/.vitepress/theme/index.ts)（主题入口文件）：

```js
enhanceApp({ app }) {
  app.component('Home', Home)
},
```

这里注册的名字 `'Home'` 是字符串，Markdown 文件里写的 `<Home />` 也是字符串——两个字符串靠人眼对齐，编译器不帮你查。把 `Home.vue` 改名成 `HomePage.vue` 而忘了改注册点，Markdown 里的 `<Home />` 就找不到组件——静默失效，页面上只留下一行字面文本。规范同时禁止「在注册点之外 glob 批量注册」（把目录下所有组件自动全部注册，名字对不对没人知道）。「官方 multi-word 组件名规则在此显式豁免」——Vue 官方建议组件名用两个以上单词（如 HomePage）避免和原生 HTML 标签撞名，这里为了和注册字符串简短对齐，显式豁免。这也是维护者注里「勿再加清单」的一项：别再把它当问题提出来。

接缝二：字体入口。规则：「自托管字体的站点，theme 入口必须用 `vitepress/theme-without-fonts`」。默认主题入口会把自己内置的字体文件打进构建产物——你明明自托管了字体（2.4 节的 woff2 文件），产物里还躺着一份官方字体，访客白下载双份。theme/index.ts 第一行就是 `import DefaultTheme from 'vitepress/theme-without-fonts'`，Layout.vue 里的 import 也被注释点名「必须与主题入口同为 theme-without-fonts，否则字体资产仍会被打进产物」——两个文件都得换，漏一个就前功尽弃。

接缝三：布局插槽。规则原文「footer 仅在无 sidebar 的页面渲染——要页脚走主题插槽或自定义组件」，布局级定制「先查主题 Layout 插槽与官方 CSS 变量族」。[Layout.vue](https://github.com/fangkun119/agent-os-poc/commit/6c168a748da3c537c9231717385cfe4ad36d7e99/website/.vitepress/theme/components/Layout.vue) 是「插槽定制」的极简示范：整个组件只有 16 行，把默认主题的 Layout 原样包了一层，只用一个插槽位 `#doc-after`（文档内容之后的区域）压制非主页的默认内容。不替换、不重写，只在主题留的「插座」上插自己的东西——这就是「先查插槽」的含义。

### 5.6 组件语言与块形态（成组略讲）

一条纯约束性规则，成组交代：「组件为无 `lang="ts"` 的 `<script setup>`，组件内禁 TS 语法，TS 只出现在 config 与常量文件」——这是个纯 JS 站点，TypeScript 只活在配置层。另有「每个 .vue 至多各一块 template / script setup / style scoped」；如需额外普通 `<script>` 块，仅限官方三种场景（script setup 表达不了的选项、命名导出、一次性副作用）。两个组件文件均符合：单块 template、单块 script setup、单块 style scoped，Home.vue 里无一处 TS 语法。这条的意义是把「文件长什么样」标准化，AI 每次新建组件都不需要临场决策。

## 6. 样式与主题（theme/custom.css）

样式章的规则密度最高。先补两个概念。**CSS 变量**：在 `:root`（文档根元素）上用 `--名字: 值` 定义的变量，全站任何地方用 `var(--名字)` 取值——改一处，全站生效。**scoped 样式**：`.vue` 文件里带 `scoped` 属性的样式块，编译时 Vue 会给样式选择器附加一个形如 `data-v-xxxx` 的属性条件，让它只命中本组件模板里的元素，不污染别人。

### 6.1 品牌色单一来源：色板变量与两类语义色

防的事故：颜色值散落在十几个文件里，改品牌色时漏掉两处，页面上出现「一家人不齐」的绿。

custom.css 的 `:root` 里集中定义了全部颜色变量——画布、面板、线条、文字、accent（品牌强调色）各一族，全部以 `--aos-` 开头。组件端 Home.vue 的样式头注释立了军令状：「色板与字阶一律消费 custom.css 的 --aos-* 变量」——翻遍它的 680 行样式，所有颜色都是 `var(--aos-...)`，没有一处硬编码色值。

规范还做了一层更细的切分：「语义色分两类」。**固定语义色**永不随色板联动——`--aos-dot-red/yellow/green` 三个变量是 macOS 终端窗口的三个圆点，那三个颜色是全世界用户的肌肉记忆，品牌换什么色板它们都不动。**品牌语义色**（`--aos-signal-*` 状态族）属于色板的一部分，随定稿联动——`--aos-signal-ok` 和品牌绿 `--aos-accent` 同值，因为「绿=健康=品牌」正是这个站点的视觉隐喻。区分这两类，是为了改色板时知道哪些跟着走、哪些原地不动。

规范还给权威出处定了规矩：「定稿色板的权威出处由 custom.css `:root` 头注释指向，色板换版时同步更新指针」。custom.css 头注释指向色板 v3「机房 LED」的定稿记录。这里发现一个真实的小瑕疵，按「代码为准」原则如实记录：Home.vue 样式头注释写的还是旧色板名「琥珀荧光」。恰好从反面证明了这条规范的价值——多处引用色板名时，必须有唯一权威出处，否则注释自己会漂移（详见文末设计决策记录第 2 条）。

### 6.2 无条件深色画布：appearance: false 的连锁纪律

这个站点是「单主题」站点：永远是深色，没有浅色模式，导航栏上也没有深浅切换按钮。config.mts 里 `appearance: false`，注释写明「isDark 恒 false：永不写 html.dark、切换按钮原生不渲染」。

这条规范要求「新增样式按深底浅字假设编写」，并禁掉两种写法。其一，「`.dark` 作用域变体是死代码」——很多项目用 `html` 标签上的 `dark` 类切换深色，而这里 `appearance: false` 意味着这个类永远不会出现，写 `.dark .foo {...}` 就是永远不生效的死代码。其二，「`prefers-color-scheme` 媒体查询同样禁止」——这是浏览器提供的「跟随用户系统深色偏好」的机制。

你可能会问：站点都锁死深色了，还怕用户系统开深色模式吗？怕，而且恰恰因为锁死了才怕。`prefers-color-scheme` 不受站点配置控制，用户系统一开深色，你写的媒体查询就真实生效——比如给浅色系统准备的补救样式此刻反过来污染深色画布。规范把这种「以为不生效其实会生效」的东西点名为画布破坏者。

留一条活口：「浅色背景仅限刻意反差段，且必须配套深色文字类」。整个代码库里唯一的「浅色」是 custom.css 里 `--vp-c-bg-elv` 的注释——它覆盖的是 VitePress 弹出菜单（语言切换、下拉）的底色，注释写明「漏映射时浅色 --vp-c-text-1 落在白底上不可读」：主题内部有个默认白色底，不覆盖它，深色站点上会突然弹出一个白底菜单。这不是浅色反差段，是给主题默认值补的深色覆盖。

还有一句容易被忽略的版本注记：「appearance 合法取值以所用版本实测为准（1.x 无 `'force-light'` 取值——写字符串会落入 truthy 分支变成跟随系统深色）」。写个看起来合理的字符串 `'force-light'`，效果恰恰相反。参考文档可能滞后，「以所用版本实测为准」再次出现。

### 6.3 主题覆盖只写全局 custom.css：scoped 为什么打不进去

这条防的事故：为了让某个 VitePress 内部组件（导航栏、侧边栏）换个颜色，你在自己组件的 scoped 样式里写了对它的覆盖——不报错，也不生效。

先把机制拆到零基础能懂。VitePress 的导航栏、侧边栏是主题内部的组件（类名以 `.VP` 开头，如 `.VPFooter`），不是你写的。scoped 样式的隔离原理是「编译时给本组件的元素和样式都盖一个 `data-v-xxx` 戳，样式只认带戳的元素」——而 `.VPFooter` 是主题内部组件的元素，它身上没有你组件的戳，你的 scoped 样式永远打不中它。规范把唯一例外也讲清了：「子组件根节点会同时受父组件 scoped 命中，属合法路径」——Vue 的规则是子组件最外层的那个元素会带父组件的戳。

所以解法是：「主题覆盖只写在全局 custom.css」。全局样式没有戳，谁都能命中。custom.css 里「主题内部覆盖」分节是标准示范，每条覆盖都注明压的是哪条内部规则：

```css
/* 压 base.css `button:focus-visible`（outline: 4px auto 浏览器焦点环，特异性 0-1-1
   高于全局 :focus-visible 0-1-0）：按钮与链接焦点统一为站点 2px 品牌描边 */
button:focus-visible {
```

这条注释连**特异性**（浏览器决定多条规则谁赢的打分规则，分越高越优先）的比分都写了。`.VPFooter`、`.VPHome`、`.VPPage` 三处覆盖同样每条带「压什么」的说明。

覆盖还有优先级路线：「优先覆盖 `:root` 的 `--vp-*` 变量；必须覆盖 `.VP*` 内部类时用最窄选择器」。custom.css 里「--vp-* 品牌映射」分节是第一优先级的实践：把 VitePress 自己的颜色变量（`--vp-c-brand-1` 等）全部指向站点的 `--aos-*` 变量，VitePress 自身的 UI 就整体跟随品牌色——改变量映射，不改任何内部类。只有变量映射覆盖不了的地方（如 `.VPHome` 的默认 margin）才动用最窄选择器。规范顺带点名「代码块高亮配色的唯一落点是 config 的 `markdown.theme`，不走 CSS 覆盖」——连「在哪里改高亮」这种容易找错门的配置都指了路。

你可能会问：为什么不干脆把所有样式都写进 custom.css，放弃 scoped？因为 scoped 管的是「你自己的组件互不干扰」，custom.css 管的是「对主题内部的覆盖」——两者是分工，不是替代。

### 6.4 写法增量纪律：!important、分节与禁 ID（成组合讲）

三条关于「往 custom.css 里加东西」的格式纪律，合成一节。

「`!important` 只准 proactive 不准 reactive」——**!important** 是 CSS 里「强制赢」的标记。proactive 指主动用它压第三方（VitePress）的内部规则，保证必胜；reactive 指用它压自己的规则——那说明你的选择器已经打架了，该去修打架本身。对照代码：custom.css 里 `!important` 恰好三处（`.VPFooter`、`.VPHome`、`.VPPage`），全是压 VitePress 内部默认样式，一处「自己压自己」都没有。

「新规则落入既有分节（盒线注释分隔的区块）或新开分节」——custom.css 用 `/* ── 分节名 ── */` 的盒线注释分成八个区块（字体、色板、字阶、--vp-* 映射、画布、可访问性、内部覆盖……），任何新样式都有明确的归属格。

「禁新增 ID 选择器」——**ID 选择器**（`#header` 这种）特异性极高，一旦出现，后面任何类选择器都压不过它，样式表就失去可控性。grep 证实全文件零 ID 选择器。

同一族里还有一条前瞻纪律：「禁止把 backdrop-filter 挂在 nav 祖先级容器——会使 fixed 定位的移动端菜单塌陷」。**backdrop-filter** 是毛玻璃模糊效果，会让浏览器在滚动时反复重算模糊区域，且会改变 fixed 定位的行为。当前代码里没有用 backdrop-filter（grep 证实），这条属于「立项时先登记的雷区」。「禁止用 vite alias 替换内部组件」也属同类：替换内部组件短期痛快，升级 VitePress 时内部一改全盘崩。配套动作是「升级 VitePress 的提交必须 build + 目检 nav/sidebar/doc——内部类改名时覆盖静默失效无报错」：内部类名一变，你覆盖的 `.VPFooter` 就打空了，还是那个词，静默。

### 6.5 动效纪律：一个编排时刻 + reduced-motion 门控

这条防两类事故。其一，「动效满地开花」：每个组件都加一点淡入、弹跳、视差，页面变成游乐园，访客晕头转向。其二，「动效伤人」：一部分人对动画有生理性不适（前庭障碍用户看到大面积运动会眩晕），系统里有个开关——**prefers-reduced-motion**（用户在操作系统里声明的「减少动效」偏好），规范要求所有动画包在这个门控里：「门控下内容静态完整呈现，不得留半成品状态」。

代码是双重门控。第一层在 custom.css：全局媒体查询把所有元素的动画和过渡一律静态化。第二层在 Home.vue 的 `onMounted` 里：JS 注入动画延迟前先查 `window.matchMedia('(prefers-reduced-motion: reduce)').matches`，命中就直接 return，动画类都不加——JS 驱动的动画不会被 CSS 门控拦住，所以 JS 这层必须自己查。

「全站至多一个载入编排时刻（当前为 hero 终端逐行显现），禁 scroll-jack、滚动触发 reveal、视差」——**scroll-jack** 指劫持滚轮行为强行控制页面滚动，是体验杀手清单第一名。Home.vue 里那个唯一时刻被注释郑重登记：「唯一编排时刻：hero 终端逐行显现（≤600ms）」——实现上 `Math.min(i * 30, 570)` 把最大延迟钉死在 570 毫秒，和注释的 ≤600ms 对得上。「新增动效先在本条登记岗位」：想加新动画，先来规范这里占坑，防止第二个、第三个编排时刻悄悄冒出来。

### 6.6 可访问性地板：对比度、焦点、可达名

**可访问性**（accessibility，常缩写 a11y）指视觉障碍、运动障碍用户也能用。规范立了三条地板线，代码逐条有落实。

对比度：「文字对比度 ≥4.5:1（大字 ≥3:1）」——**对比度**是文字颜色和背景颜色的明暗差比值，太低看不清。custom.css 色板注释直接写进变量定义：「弱文字两档对 bg 均 ≥4.5:1，装饰元素才允许更暗值」——最暗的文字档 `--aos-text-3` 也踩在线上，装饰性的更暗颜色被明确限制用途。

键盘焦点：「键盘焦点必须有可见样式（`:focus-visible`，深底描边 ≥2px 带 offset）」——不用鼠标的用户用 Tab 键在链接间跳，焦点必须有看得见的标记，否则不知道自己在哪。custom.css 里全局 `:focus-visible` 给了 2px 描边加 2px 偏移；因为浏览器给按钮的默认焦点环特异性更高，又有 button 专项覆盖（6.3 引用过那条带特异性比分的注释）。「反差底色区内改用底色描边」的要求体现在色板变量设计上——`--aos-on-accent-*` 一族专门给「品牌色底子上的元素」用深色文字和描边。

可达名：「图片 alt / 控件可达名不回退」。Home.vue 里的架构图配了双语 alt（图片加载失败或读屏软件朗读时的替代文字）；架构图外层容器因为要横向滚动，加了 `tabindex="0"`（让键盘方向键能聚焦到滚动区）和 `role="region"` 加 `aria-label`（告诉读屏软件这是什么区域）；连装饰性的分隔点都标了 `aria-hidden="true"`（让读屏跳过）。config.mts 里 logo 的注释「alt 空则链接无可达名」补上了导航侧——logo 是整个导航栏唯一的可点击物，alt 就是它唯一的名字。

### 6.7 组件 scoped 纪律：类开头、:deep、禁内联 style

最后一条样式规则，管组件内部怎么写样式，三条全在 Home.vue 上验收。

「选择器首 token 必须是类」——scoped 样式编译后变成「原选择器 + 属性条件」，比如 `div` 变成 `div[data-v-xxx]`；如果首 token 是裸元素名再叠加属性选择器，浏览器匹配起来比单类名慢数倍。Home.vue 的做法是最外层一个 `.home` 根类，内部所有选择器都从它出发（`.home .hero`、`.home a`），没有任何裸元素开头的全局扫描。

「`:deep()` 是唯一穿透出口且须注明理由」——**`:deep()`** 是 scoped 样式里强行命中子组件内部元素的语法。全文件 grep 不到一处 `:deep()`：这个单组件站点确实用不着穿透。「禁用位置序数选择器（`nth-of-type` 等）定位内容段」防的是和数据驱动互斥的写法：「与数据驱动 + v-for 互斥，插入条目即错位」——如果你靠「第 2 个卡片是绿色」这种位置定位样式，往数组里插一条新数据，所有序号后移，样式全错位。这个站点的卡片差异化全靠数据里的字段（如 `roadmap-card--active` 由 `p.active` 控制），没有一处按位置上色。

「模板禁写 `style="…"` 内联样式属性」——内联样式一绕开 scoped 隔离（无法被覆盖），二绕开色板审计（颜色审计时 grep 变量就漏掉它）。Home.vue 的应对是最漂亮的证据：hero 终端逐行动画每行延迟不同（第 0 行 0ms、第 1 行 30ms……），按惯性写法就是往模板里塞 `:style="{ animationDelay: ... }"`。代码注释点名了规范：「模板内联 style 属性被 website/CLAUDE.md 禁止（绕开 scoped 隔离与色板审计），故在 mounted 以 JS 注入动画时序（仅时序，非样式定值）」——用 JS 设置动画延迟，既绕不开审计时漏掉颜色（注入的只是时序数字，不是颜色尺寸），又不污染模板。规则的意图（色板可审计、样式可覆盖）被完整继承，实现路径另辟。

## 7. 文档内容（docs/ 与 zh/docs/）

### 7.1 本章现状：证据对象尚未诞生

如实交代：这一章六条规范面向 `docs/`（英文文档页）和 `zh/docs/`（中文文档页），而这两个目录当前不存在——站点只交付了双首页，文档站属于路线图第三阶段。所以本章多数条目没有落地证据，下面按「防什么」讲清原意，能落到现有代码的旁证单独指出。规范把这一章提前写好，是给将来的文档页立规矩。

### 7.2 内容保真与溯源链接制度

六条里当前唯一有完整证据的是「内容保真」：「每条实质性陈述（数字/类名/端点/机制）都应能在来源章节找到出处，找不到出处不写，禁止凭模型自身知识补写细节」。

防的事故在 AI 时代极其高发：AI 写介绍页时，把训练数据里的「行业常识」当成这个项目的事实写上去——数字是编的、类名是别的项目的、机制是想当然的。访客按页面写的 API 路径去调用，404。

Home.vue 落地了一套完整的「溯源制度」：每个能力卡片和场景卡片都带 `source: docRefs(['DA 5.2', 'TS 11.1'])` 字段，`docRefs` 函数把它转换成指向仓库权威文档（需求文档、技术方案）对应章节的链接，渲染成卡片角落的「⟶ DA 5.2 · TS 11.1」——页面上的每个数字、每个机制声明，都能一键点回出处。脚本注释直接引用了制度名：「页面事实仅取自权威文档」。数据条旁边的免责声明是同一纪律的表达：「性能为验收目标，非承诺值」——数字有出处，出处的性质（目标而非承诺）也如实标注。

### 7.3 中文排版与占位符记法（旁证落地）

「中文排版」条在现有组件文案里有旁证。「中文与英文/数字之间加空格」：Home.vue 中文文案是「9 个内置 Tool」「每天 8:00」「基于 Java 的企业级 Agent OS」——中英文之间都有空格。规范还留了防过度矫正的例外：「度数与百分比紧跟数字」。「专名按官方拼写」：GitHub、VitePress、Kubernetes 这类词不写小写回退。「视觉全大写用 `text-transform` 实现，不把全大写字符串硬编码进源码」有精确证据：hero 标题上方的标签文字，源码里是 `t('企业级 Agent OS', 'The Enterprise Agent OS')` 常规大小写，样式里 `text-transform: uppercase` 负责视觉变大写——检索源码的人看到的是可读文本，屏幕阅读器朗读的也是正常文本。

「示例占位符统一记法」条：「环境变量引用写 `${VAR}` 形态（组件内模板字符串按转义规则写 `\${VAR}`）；用户填入值统一 `your-xxx-here` 形态」。ctaLines 里的 `export DEEPSEEK_API_KEY=your-key-here` 就是 `your-xxx-here` 家族的实际使用。全站只此两种记法，读者在任何页面看到的占位符长得一样。

## 9. 收尾：这份规范真正教了什么

合上文件，三句话带走。

第一句：**前端最大的坑不是报错，是静默失效**。写错层级的配置、臆造的字段名、scoped 里打不进子组件的覆盖、不生效的 `.dark` 变体——全都安静地「成功」了。这份规范一大半的篇幅在做同一件事：把「不报错」的地方变成「有明确对错」。你自己的项目里，凡是「不报错但可能不生效」的环节，都值得写一条。

第二句：**单一来源是治漂移的万能药**。颜色有色板、常量有 constants.ts、权威出处有指针、注释只写事实不许讲故事——全是在对抗「同一件事在多处各说各话」。文中发现的三处注释漂移（旧色板名、旧字体描述）恰好是反面教材：单一来源立起来了，引用处还是会老，所以规范连「色板换版时同步更新指针」这种动作都写死了。

第三句：**给 AI 的规范就是给人省下的 review**。每条规则都对应一类 AI 高频错误：臆造字段、叙事型注释、顺手重构、把示例里的 `${}` 写炸构建、靠位置定位样式。把错误清单前置成纪律，AI 的产出就从「能跑」变成「符合家规」。

迁移到自己项目的路径，维护者注已经写好：这份文件本身就是模板，拷进你的 VitePress 项目，按文末「站点参数清单」九项逐项核对（locale 组合、部署形态、appearance 取值、是否自托管字体、是否收录镜像、siteTitle 与 titleTemplate、组件语言、构建入口、断点与色板状态），删掉不适用的条件式条款。规则跟着部署形态走，而不是拷过去就完事。
