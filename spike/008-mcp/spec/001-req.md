## 一、遇到了什么问题

一句话：MCP 是 AgentOS 的验收硬依赖，但支撑它的 MCP Java SDK 从未实测过，而且它排在最挤的第二周——当场爆雷没有任何缓冲。

### 1.1 验收硬依赖：方式一 MCP 跑通是发布硬条件

- DemandAnalysis.md - 13 验收标准 的功能验收清单两条原文："Plugin Tool 接入（方式一零代码 Agent 目录 + MCP 跑通；方式三 @Tool 注解示例跑通）"、"MCP Client 集成、CLI Channel"。
- DemandAnalysis.md - 13 验收标准 的场景验收的 Demo 二（每日科技日报），验证能力一栏写明"能力四（Plugin Tool 方式一 Agent 目录零代码 + 方式二 MCP）"，验收标准要求业务方"全程不写 Java 代码，只写 `AGENT.md`（含 `schedules` 字段）并在 Agent `skills/` 绑定公共 Skill，再配置 `mcp_servers.yaml`"。实施细节见 TechnicalSolution.md - 12.2 Demo 二。
- DemandAnalysis.md - 13 验收标准 明文：两个 Demo 跑通是核心功能发布的**硬条件**。

### 1.2 未实测的风险敞口：MCP Java SDK

- TechnicalSolution.md - 1.2 整体技术栈 的技术栈清单第 8 项原文："**MCP Java SDK**（MCP Client 集成，社区项目，可能需要部分自实现）"。TechnicalSolution.md - 1.2 整体技术栈 的十项技术栈里，只有第 8 项（MCP Java SDK）挂着"可能需要部分自实现"的存疑标注（第 10 项 Micrometer 属扩展阶段）。
- spike/007 验证的是 Spring AI / SAA 主线（其 README 的 D1-D4 决议、E1-E9 实验），全程没有触碰 MCP Java SDK——`spike/007-react-loop/` 全目录无 MCP Java SDK 的依赖与代码（唯一 "MCP" 字样是其 spec/002-req.md 工具表对 Context7 检索工具的说明）。
- 版本现状（Maven Central，repo1.maven.org，2026-09-14 查证）：
  - `io.modelcontextprotocol.sdk:mcp` 全线共 40 个版本，从 0.7.0 走到 2.0.1（当前 release）：0.x 线 25 个（0.7.0 至 0.18.4）、1.x 线 1.0.0 至 1.1.4、2.x 线已到 2.0.1；
  - 项目锁定的主线上，`org.springframework.ai:spring-ai-mcp:1.1.2` 的 POM 传递依赖 `io.modelcontextprotocol.sdk:mcp:0.17.0`（另有 mcp-spring-webflux、mcp-spring-webmvc 同为 0.17.0）——照单引入 spring-ai-bom 时，进来的是一个 0.x 版本的 SDK；
  - 也就是说：TechnicalSolution.md - 1.2 整体技术栈 落笔时的"0.x 版本线"语境对框架托管路径仍然成立，但 SDK 独立使用时已到 2.x。版本跨度大、跨线 API 稳定性未知、该跟哪个版本走，正是要实测的问题（M2）。

### 1.3 排期无缓冲

- DemandAnalysis.md - 11 里程碑规划 的第二周（3 小时）排了三件事：Memory 长期记忆、文件/Shell Tool、MCP Client 集成（连接外部 MCP server）；TechnicalSolution.md - 13 实施节奏 的第二周同样列有 `McpClientService`（连接外部 MCP server）条目。
- "第二周 MCP 当场爆雷"没有任何预案兜底；DemandAnalysis.md - 12 风险与未决事项 的风险表也没有 MCP 专项风险条目。
- 一旦第二周才发现 SDK 不可用或 API 与预期不符，同周的 Memory 与文件/Shell Tool 会被连带挤压，"每周有可演示成果"的节奏就断了。

### 1.4 评审决议

2026-09-13 设计评审 Q4 决议：项目进入实现阶段之前补 MCP spike，出口条件三条——**传输层结论、版本锁定、降级路径决议**。本 spike 即该决议的执行，对应 M1、M2、M8 三问。

## 二、为何需要 Spike

三条独立事实叠在一起：

| # | 事实 | 单独看 | 叠加后果 |
|---|---|---|---|
| 1 | 方式一 MCP 跑通是 DemandAnalysis.md - 13 验收标准 的发布硬条件 | 必须做，没有"降级不做"的选项 | 风险无法靠砍需求回避 |
| 2 | MCP Java SDK 从未实测，版本线从 0.x 跨到 2.x | 存在不确定性 | 不确定性必须先探明，不能带进正式代码 |
| 3 | MCP Client 挤在第二周 3 小时里，同周还有 Memory 与文件/Shell Tool | 时间容错为零 | 爆雷即连锁延误 |

结论：风险必须在写正式代码之前，用一个独立小项目实跑代码探明。这也是仓库既定规程——spike/CLAUDE.md：写正式代码前，用独立的小项目实际跑代码来验证技术方案。

### M1 传输层范围：核心阶段 stdio-only 是否足够

- TechnicalSolution.md - 6.4 Plugin Tool 方式二 现文：MCP 工具调用经 "JSON-RPC over stdio 或 SSE" 转发。
- 核心阶段 AgentOS 是单机单体应用，MCP server 的现实来源是本地子进程（如 npx 拉起的社区 server），stdio 够用；SSE 服务于远程 server，属远程集成场景。
- 还有一条架构理由：TechnicalSolution.md - 4.2 模块组成 规定 ProfileContext 是 ThreadLocal、ReAct 循环全程禁止切换执行线程——SDK 的同步（sync）客户端与 TechnicalSolution.md - 1.1 关键技术决策 的决策三的同步阻塞执行模型天然对齐，异步传输实现引入的线程模型与该约束相抵。
- 要回答的问题：stdio-only 是否覆盖核心阶段全部场景？若结论是 stdio-only，TechnicalSolution.md - 6.4 Plugin Tool 方式二 需收窄一句"核心阶段仅 stdio，SSE 传输放扩展阶段"（联动项见 6.2 节）。

### M2 SDK 选型与版本锁定

- 要回答的问题：选定 MCP Java SDK 的版本与 Maven 坐标，并定下引入方式。两个候选（实测后二选一）：
  1. **随框架走**：用 spring-ai-bom 1.1.2 管理的 MCP 相关构件（spring-ai-mcp 传递依赖 `io.modelcontextprotocol.sdk:mcp:0.17.0`），版本兼容性由 Spring AI 官方保证；
  2. **直引 SDK**：自行指定 `io.modelcontextprotocol.sdk:mcp` 的更高版本（0.18.x / 1.x / 2.x），须实测与 Spring AI 1.1.2 的兼容性。
- 附带要定：是否引入 `org.springframework.ai:spring-ai-starter-mcp-client`（Spring AI 的 MCP Client starter，Maven Central 已确认存在 1.1.2 版本，2026-09-14 查）。starter 自带自动装配，它与 AgentOS 自持 McpClientService、不用框架自动行为的取向是否相容，要实测确认。
- 记录格式：照 spike/007 README 的 D2 决议"依赖坐标清单"格式（parent / BOM / 构件 / 版本来源逐项列明），正式实现照单引入。

### M3 工具发现：tools/list → AgentOSTool → ToolRegistry

- TechnicalSolution.md - 6.4 Plugin Tool 方式二 的 McpClientService 职责：AgentOS 启动时连接所有配置的 MCP server，调 `tools/list` 拿工具列表，把每个 MCP 工具包装成 `AgentOSTool` 注册到 `ToolRegistry`。
- 要回答的问题：SDK 的 tools/list 返回结构（工具名、描述、inputSchema）映射到 `AgentOSTool` 四方法（getName / getDescription / getInputSchema / execute，TechnicalSolution.md - 6.1 AgentOSTool 抽象）是否直接可行；一个 server 的多个工具能否批量注册。
- 对照点：MCP 工具的 inputSchema 与 Spring AI `@Tool` 生成的 JSON Schema 同为 JSON Schema 格式，理论上是直映射，spike 实证。

### M4 工具调用往返：call tool → ToolResult

- TechnicalSolution.md - 6.4 Plugin Tool 方式二 的 McpToolAdapter 职责：工具调用时经 MCP 协议转发给对应 server 执行，结果包装成 `ToolResult` 返回。
- 要回答的问题：call tool 请求发出后，结果（含出错形态：协议错误、server 报错、超时）如何映射进 ToolResult 四要素——成功标识、结果内容、错误信息、是否可重试（TechnicalSolution.md - 6.1 AgentOSTool 抽象）。
- 边界说明：MCP 工具结果可能是多段内容（文本/资源等），包装策略要在 spike 里定；工具结果体积无上限的问题已在 DemandAnalysis.md - 12 风险与未决事项 的未决事项挂账（工具返回结果的裁剪策略），本 spike 不重复展开，只在 README 如实记录实测到的结果形态。

### M5 与手动循环的接线

- 红线：禁自动 tool 执行（仓库根 CLAUDE.md 非协商原则 4；TechnicalSolution.md - 1.1 关键技术决策 的决策二）。MCP 工具的接线必须走 spike/007 README D3 的手动循环标准路径：`ToolCallingChatOptions.builder().toolCallbacks(...).internalToolExecutionEnabled(false).build()`。
- 要回答的问题：MCP 工具的 JSON schema 如何进入 `ToolCallingChatOptions` 的 toolCallbacks。两个候选：复用 Spring AI 的 MCP 工具适配（spring-ai-mcp 模块是否提供 ToolCallback 形态的现成实现，由 spike 实测确认）；或经 AgentOSTool 自己适配一层。实测定一条。
- 验证形态：在最小 ReAct 手动循环里，让 LLM 真实调用一个 MCP 工具完成闭环（LLM 发起 → 我方手动执行 MCP 调用 → 结果回灌 → LLM 给最终回答），证明 MCP 工具与内置工具在循环里"长一个样"（TechnicalSolution.md - 1.1 关键技术决策 的决策四：ReAct 循环不感知 Tool 来源）。

### M6 失联、超时、错误恢复的最小行为

- TechnicalSolution.md - 6.4 Plugin Tool 方式二 要求 McpClientService "处理 server 失联、超时、错误恢复"，但没有定义做到什么程度。spike 定核心阶段的最小行为。
- 至少实测并记录三点：① server 进程启动失败或启动即挂时，连接阶段的异常形态；② server 运行中失联（如进程被杀）时，调用阶段的异常形态与 SDK 的重连行为（有无自动重连）；③ 调用超时的表现（SDK 有无超时参数、默认值多少）。
- 设计参照（最小行为应尽量贴合，不自造新机制）：Agent 加载校验失败"不阻断启动但记录错误日志"（TechnicalSolution.md - 8.2 Profile 配置）；工具失败返回可重试标识、由 LLM 决定是否重试（TechnicalSolution.md - 4.2 模块组成 / TechnicalSolution.md - 6.1 AgentOSTool 抽象）；超时复用既有三档分步预算（TechnicalSolution.md - 7.4 关键设计点：Tool 单次默认 30s、配置化不硬编码）。

### M7 mcp_servers.yaml 字段验证与凭证红线

- 字段口径：TechnicalSolution.md - 6.4 Plugin Tool 方式二 定了四个字段 `name` / `transport` / `command` / `env`（command=stdio 方式的启动命令、env=传给子进程的环境变量）。spike 用真实 server 验证这四个字段够不够、语义是否成立。
- 密钥红线延伸：TechnicalSolution.md - 8.8 配置与密钥加载 明文把"MCP server 凭证"列入 ConfigLoader 的敏感配置范围。MCP server 自身需要凭证时，env 配置只允许写 `${环境变量名}` 占位符、经环境变量注入，不明文写配置、不完整进日志（最多 5 位前缀）。spike 的实验配置必须按此纪律执行，并验证 env 占位符经 stdio 子进程环境变量传下去的通路可行。
- 附加说明：存在两层引用——mcp_servers.yaml 全局登记"有哪些"server，AGENT.md frontmatter 的 `mcp_servers` 字段声明该 Agent 引用其子集（DemandAnalysis.md - 5.2 定义一个 Agent 的 frontmatter 结构）；工具级过滤再由 Profile 的 `tools` 字段承担（TechnicalSolution.md - 6.6 ToolRegistry）。本 spike 重点验证全局登记层的四个字段，frontmatter 过滤属正式实现范畴。

### M8 降级路径决议

- 前提：DemandAnalysis.md - 13 验收标准 的"方式一 MCP 跑通"是发布硬条件，任何降级都不降验收标准。
- 要回答的问题：若 SDK 路径被证伪（不可用或兼容性无解），为 1-2 个已知 demo server 手写最小 stdio JSON-RPC 客户端的可行性——MCP 的 JSON-RPC 消息格式公开，最小闭环（initialize 握手 + tools/list + tools/call）的实现量需实测评估。
- 决议形态：若触发降级验证且可行，记为技术债（自研客户端的正式化放后续），TechnicalSolution.md - 1.2 整体技术栈 的第 8 项替换为降级决议 + 技术债记录；DemandAnalysis.md - 13 验收标准 一字不动。

## 四、建议采用的方法

1. **真实连接现成社区 server。** 选 1-2 个现成社区 MCP server 做被连对象，推荐 MCP 官方维护的 everything server 与 filesystem server（均为 stdio 传输的本地子进程；spike 执行时以官方仓库 modelcontextprotocol/servers 的当前形态为准）。用它们完成 tools/list（M3）与工具调用往返（M4）。
2. **最小 ReAct 手动循环跑真闭环。** 参照 spike/007 README D3 的手动循环标准路径**重写**（007 已封存、不拷代码），让 LLM 经手动循环真实调用一个 MCP 工具完成一次任务闭环（M5）。LLM 依赖照 007 D2 坐标清单引入；模型密钥按密钥红线先 source 仓库外脚本 `~/.agent-os-poc/script/agent-os-env.sh` 加载；MiniMax-M3 思考内容混在 `<think>` 标签里，断言前剥离（spike/007 README 附带实测结论）。
3. **对照实验只在必要时做。** 仅当 SDK 路径失败（M2/M3/M4/M5 被证伪）时，才手写最小 JSON-RPC 客户端对同一 server 做降级验证（M8）；SDK 路径走通则不写。
4. **工程形态遵守 spike 规程**（spike/CLAUDE.md）：独立 Maven 项目、自带 pom.xml、构建在 spike 目录内执行、不进根 pom 的 modules；基线版本沿用 007 D1/D2——parent `spring-boot-starter-parent:3.5.16` + JDK 21 + 双 BOM（`spring-ai-alibaba-bom:1.1.2.0` + `spring-ai-bom:1.1.2`）。
