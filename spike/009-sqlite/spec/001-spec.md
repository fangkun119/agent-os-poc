### 2.1 条款 D1（P0）：ddl-auto=update 对既有表的真实行为

**行为规约**：实验必须在本 spike 版本组合（第 1 章）上，对"表已存在、实体只加一个字段（不删不改旧列）"场景——V1 建表与 V2 加列两次启动共用同一库文件（req 2.1 实验方法第 2 步）——产出明确二选一实测结论：

- (a) 新列自动出现（ALTER TABLE ADD COLUMN，即加列语句，发生）且旧数据保留；
- (b) 表结构不变（记录实际现象：启动静默跳过，或报错——报错时记录异常类型与消息原文）。

同时必须把"首建"与"演进"两条路径分开下结论：全新库文件用加列后实体（V2）首建正常建表。表结构快照（`PRAGMA table_info` 输出，SQLite 的表结构回读命令）与启动日志落证据文件。

**通过判据**：

1. 基线实体（V1）与加列后实体（V2）两次启动各有一份 `PRAGMA table_info` 快照落 `logs/`，两份可逐列对照；
2. V1 阶段插入的样本行在 V2 阶段可查询、行数不变（对照值留档）；新列在旧行上的取值如实记录；
3. 全新库文件首建快照落 `logs/`，`PRAGMA table_info` 显示 V2 全部列；
4. 结论行明确写 (a) 或 (b)、无第三种模糊态；(a) 触发 req 第 7 章联动 1 的改写动作，(b) 维持 TechnicalSolution.md - 9.2 SQLite 关系型数据现行口径（版本化手工迁移脚本）。

### 2.2 条款 D2（P0）：WAL 三件套 pragma 经连接串的生效性

**行为规约**：实验必须对连接串三参数 `journal_mode=WAL`、`busy_timeout=5000`、`synchronous=FULL` 逐参数给出"生效/不生效"结论，判定手段=PRAGMA 回读（执行 SQLite 的参数查询语句、读回当前生效值）。正向组按生产同款装配执行（req 2.2 实验方法第 1 步）：按 agentos/CLAUDE.md 第 3 章单一入口约束配 `spring.datasource.url` 带三参数，经 HikariCP（Spring Boot 默认连接池，默认不透传独立 pragma——连接串参数由此成为主验证路径）取连接回读。负向对照分两类做：

- journal_mode 是写入库文件的持久属性：负向证据用**全新库文件**无参打开回读（同一文件无参重开必读 wal，不作负向证据）；
- busy_timeout 与 synchronous 是连接级参数（不落文件、随连接存在）：用同一库文件不带参数重开对照成立。

三条缺省值都以实测为准、不预设（synchronous 缺省值随驱动构建与日志模式而变，req 2.2 实验方法第 6 步注记）。另须覆盖两项：`-wal`/`-shm` 伴生文件存在性检查；拼错参数探针（验证 agentos/CLAUDE.md 第 3 章"拼错整条静默忽略"的风险是否属实，并记录驱动对未知参数有无任何报错或日志）。备选路径（`SQLiteConfig` 注入，xerial 驱动的配置对象）仅当连接串参数某项不生效时启用；备选若与 agentos/CLAUDE.md 第 3 章"禁第二入口"条款冲突，移交 req 第 7 章联动流程、不在 spike 内自行放宽。

**通过判据**：

1. 正向组三项回读落 `logs/`：`PRAGMA journal_mode`=`wal`、`PRAGMA busy_timeout`=`5000`、`PRAGMA synchronous`=`2`（FULL 的官方数值）；
2. 负向组回读落 `logs/`：journal_mode 用全新库文件回读（预期 delete，以实测为准）；busy_timeout 与 synchronous 用同一库文件无参重开回读，缺省值实测记录；
3. 执行一次写入后的库目录列表落 `logs/`，`-wal` 与 `-shm` 文件出现；
4. 拼错探针行为记录在案：拼错参数名（如少一个下划线）后回读值不变，并记录驱动有无报错或日志（预期：静默忽略坐实）；
5. 任一参数不生效时：备选路径必须给出"哪条路可行"的确定结论（含可行绕法记录），同样算通过。

### 2.3 条款 D3（P0）：轮原子提交事务与并发 BUSY 面

**行为规约**：实验必须建立四条观察，全部落证据：

1. 正常路径：单个事务内插入一整轮 5 行（1 条 user + 2 条 assistant + 2 条 tool），提交成功；事务内分配的主键 id 连续（对照 TechnicalSolution.md - 9.2 SQLite 关系型数据 (2) 的"单写者下事务内行 id 连续"）；
2. 异常路径：事务内插入后抛 RuntimeException，回滚后零行落库（对照 agentos/CLAUDE.md 第 3 章"持久层抛异常即回滚并放弃该工作单元"条款）；
3. 并发组一（等待成功面）：两个裸 JDBC 连接（DriverManager 直连、不经连接池，隔离连接池语义）交叠写同一库（连接串写法与 D2 已验证的写法一致，req 2.3 实验方法第 3 步）；占用方的写事务持有时长小于 busy_timeout=5000ms。预登记预期分支：另一连接（B）等待后成功。若实测为异常分支，作为与设计假设的偏差照实登记进 README 附带发现（两分支都可接受，但必须登记到明确一栏）；
4. 并发组二（超时错误面）：占用时长超过 busy_timeout=5000ms，拿到 B 连接的异常类型与完整消息原文（BUSY 错误在 JDBC 层的面貌，供正式实现"报错与有限重试出口"设计引用）。

实验遵守短事务纪律：事务体内只做写库与计时等待，不仿真 LLM 调用、tool 执行等行为（那是正式实现红线，agentos/CLAUDE.md 第 3 章"物理事务尽可能短"条款）。

**通过判据**：

1. 正常路径：行数=5、事务内 id 连续，两个数字实测留档；
2. 异常路径：回滚后查询行数=0；
3. 并发组一：实测结果落档，并明确标注命中预登记预期（等待后成功）或偏差（异常）；
4. 并发组二：BUSY 异常类型名与消息原文样本落档；
5. 四条证据各自在 `logs/` 有对应日志段。

### 2.4 条款 D4（P0）：社区方言常规 JPA 面够用性

**行为规约**：实验必须对社区方言（hibernate-community-dialects 6.6.53.Final 的 `org.hibernate.community.dialect.SQLiteDialect`）在常规 JPA 面上建立四组观察：

1. CRUD 全链：save → findById → 字段修改再查 → delete，全程无错；
2. 类型映射与主键：一个实体覆盖 Boolean、long、String、LocalDateTime 四类字段；主键 `GenerationType.IDENTITY`（数据库自增主键，agentos/CLAUDE.md 第 3 章 SQLite 主键条款）；实体带 id、create_time、update_time 三列（同章新表条款，顺带覆盖时间列映射）；
3. DDL 实证：建表语句中主键列含 `INTEGER ... AUTOINCREMENT` 字样（AUTOINCREMENT 关键字必须真出现——TechnicalSolution.md - 9.2 SQLite 关系型数据 (2) 的 `session_messages.id` 依赖此语义）；各字段列的声明类型逐列实录（SQLite 列类型是建议性的，实际落什么存储形态以实测为准）；
4. 往返校验：四类字段写入后读出逐字段比对；LocalDateTime 加两组边界样本（纳秒精度、跨时段时刻），记录实际存储形态（文本串还是整数）与往返是否无损。

发现的坑逐条三级归类：阻断（正式实现没法用）/ 有绕法（记录绕法）/ 无碍（仅记录差异）。

**通过判据**：

1. CRUD 四步断言全过（断言用 AssertJ——Java 断言库、本仓编码规范指定的测试断言出口；输出落 `logs/`）；
2. 四类字段往返逐字段比对结果落档，全部一致；
3. 建表 DDL 快照落 `logs/`，AUTOINCREMENT 关键字在主键列声明中可检索命中；
4. 各字段存储形态实录落档；
5. 若有坑：坑清单 + 三级归类落档；"阻断"级条目写明影响哪些表与字段，并列入 req 第 7 章联动 5。

### 2.5 条款 D5（P1）：synchronous=FULL 的提交耗时量级

**行为规约**：实验必须在**文件库**上跑两组对照（`:memory:` 内存库没有真实 fsync，测不出差别）：组 1 synchronous=FULL、组 2 synchronous=NORMAL；其余条件全同——同机、同库结构、WAL 开、每次提交事务写 1 行、连续 1000 次提交。计时用 `System.nanoTime`。结论必须完成三件事：

1. 给出两组各自的总耗时与单次提交均值（ms）；
2. 算出 FULL 相对 NORMAL 的写放大倍数；
3. 按"一轮 = 1 次消息事务 + 每迭代 2 次审计事务（审计两表逐次即时落库，TechnicalSolution.md - 4.3 关键设计点 (2)）"换算：10 次迭代一轮 = 1 + 2×10 = 21 次提交事务，算其提交开销合计，对照"60s 级 LLM 调用"量级。

实验控制：避开其他重 IO 进程干扰、机器空闲时跑；环境记录（执行日期、机型、磁盘类型）进结论，结论一律标注"本机量级实测"。

**通过判据**：

1. 两组数字落 `logs/`：总耗时、单次提交均值（ms）、FULL/NORMAL 倍数；
2. 结论明确回答：单次 FULL 提交均值是否 < 10ms（req 设定的"毫秒级"判据线）——成立则维持 TechnicalSolution.md - 9.2 SQLite 关系型数据现行表述，不成立则触发 req 第 7 章联动 3 改写；
3. 数字全部实测，禁估算。
