### 2.1 D1：ddl-auto=update 对既有表的真实行为（P0）

**验证问题**：Hibernate 6.6.53.Final 的 `spring.jpa.hibernate.ddl-auto=update` 在 SQLite 上，遇到"表已存在、实体新加了字段"时，到底会不会自动 `ALTER TABLE ADD COLUMN`（加列）？TechnicalSolution.md - 9.2 SQLite 关系型数据的工程风险提示写"`update` 在 SQLite 上只做逐条 `CREATE TABLE`，不涉及 `ALTER`"。这条断言是成立还是过强，直接裁决挂账一（2026-10-03 设计评审 Q4）。

**实验方法**：

1. 建基线：实体 V1（两个普通字段）+ ddl-auto=update 启动一个 Spring 上下文，建表并插入样本行。用 `PRAGMA table_info(<表名>)` 回读表结构留档。
2. 加列再启：实体改 V2（**只加**一个字段，不删不改旧列），用**另一个** Spring 上下文再启动（同一 `application.yaml`、同一库文件、ddl-auto=update 不变）。
3. 回读对照：`PRAGMA table_info(<表名>)` 查新列是否出现；查 V1 阶段插入的样本行是否还在、新列在旧行上的取值。
4. 首建对照：换一个全新库文件，直接用实体 V2 首建，确认 update 的首次建表路径正常——把"首建可靠"与"演进可靠"两件事分开下结论。
5. 表结构快照与启动日志全部落证据文件（`PRAGMA table_info`（SQLite 的表结构回读命令）输出 + sqlite_master（SQLite 存放库内全部表结构与建表语句的系统表）查询输出 + 启动日志）。

**通过判据**：实验给出明确二选一，两种都算通过：

- (a) 新列出现在 `PRAGMA table_info` 输出中、旧数据保留 → "不涉及 ALTER"断言**过强**，触发回填改写（见第 7 章结论回填联动（预登记）的联动 1）；
- (b) 表结构不变（无论启动静默跳过还是报错，记录实际现象）→ 断言**成立**，第三周按"版本化手工迁移脚本"口径执行（TechnicalSolution.md - 9.2 SQLite 关系型数据 现行写法）。

**优先级**：P0。不先拿到答案，第三周"表结构演进"的写法就没法定。

### 2.2 D2：WAL 三件套 pragma 经连接串的生效性（P0）

**验证问题**：xerial 驱动 3.49.1.0 下，连接串 `jdbc:sqlite:...?journal_mode=WAL&busy_timeout=5000&synchronous=FULL` 三个参数是否真生效？怎么回读证明？HikariCP 默认不透传独立 pragma（agentos/CLAUDE.md 第 3 章），连接串参数这条绕法是否可靠？

**实验方法**：

1. 正向组：Spring Boot 数据源按 agentos/CLAUDE.md 第 3 章的单一入口约束配 `spring.datasource.url` 带三参数（经 HikariCP，不自建 DataSource Bean）。启动后从连接池取连接，依次执行 `PRAGMA journal_mode` / `PRAGMA busy_timeout` / `PRAGMA synchronous` 回读，输出留档。
2. 负向对照（三个参数分两类做）：journal_mode 是写入库文件头的**持久属性**——同一库文件不带参数重开回读仍是 wal，读不出缺省值（2026-10-09 本机 sqlite3 3.51.0 实测：全新文件无参打开=delete → 设 `PRAGMA journal_mode=WAL` 后回读=wal → 同文件关闭后不带参数重开回读仍=wal）。所以 journal_mode 的负向证据改用**全新库文件**（从未设过 WAL）无参打开回读 delete。busy_timeout 与 synchronous 是**连接级参数**（不落文件、随连接存在），用同一个库文件不带参数重开对照成立。三条缺省值都以实测为准、不按文档想当然（journal_mode 预期 delete，另两条不预设）。缺省值与设定值的差异就是"参数生效"的证据。
3. 文件面：执行一次写入后列库目录，确认 `-wal` 与 `-shm` 伴生文件出现（WAL 三件套实体证据）。
4. 拼错探针：故意写错一个参数名（如 `journalmode`，少一个下划线），回读确认行为。目的：验证 agentos/CLAUDE.md 第 3 章"拼错整条静默忽略"的风险是否属实。同时记录驱动对未知参数有无任何报错或日志。
5. 备选路径：仅当连接串参数某项不生效时启用——改测 `SQLiteConfig`（xerial 驱动的配置对象）注入路径，记录可行绕法。连接串参数路径生效时不测备选（agentos/CLAUDE.md 第 3 章已收口单一入口）。备选路径若可行、但与第 3 章"禁第二入口"条款冲突，属规范修订事项：走第 7 章结论回填联动（预登记）流程，不在 spike 内自行放宽。
6. 注记：synchronous 的 SQLite 缺省值**不恒为 FULL（2）**——它随驱动构建与日志模式而变（2026-10-09 本机 sqlite3 3.51.0 实测：WAL 库文件上无参回读 1，全新 delete 模式文件与 `:memory:` 内存库回读 2）。此项负向对照以实测为准、不预设；正向组显式设 FULL 后回读 2 不受影响。生效性的**差异证明**由另外两项代表：journal_mode（全新文件 delete→设 WAL 后 wal）与 busy_timeout（缺省值→5000）。三者走同一连接串机制，一项生效即证明机制通。

**通过判据**：

- `PRAGMA journal_mode` 回读 `wal`（正向组）vs `delete`（负向组用**全新库文件**；同文件无参重开必读 wal——WAL 是库文件持久属性，不作负向证据）；
- `PRAGMA busy_timeout` 回读 `5000`；
- `PRAGMA synchronous` 回读 `2`（FULL 的官方数值，实测记录）；
- 写入后库目录出现 `-wal`、`-shm` 文件；
- 拼错探针的行为记录在案（预期：回读值不变且无报错，坐实"静默忽略"风险）；
- 全部回读输出与文件列表落证据日志。

若某参数不生效：备选路径必须给出"哪条路可行"的确定结论，同样算通过。

**优先级**：P0。DemandAnalysis.md - 8.2 可靠性"已写入的 Session 数据保证不丢"的机制前提就是 WAL + FULL；这条不绿，可靠性承诺没有机制支撑。

### 2.3 D3：轮原子提交事务可行性（P0）

**验证问题**：单事务写整轮消息（轮首 user 行 + 多条 assistant/tool 行 + 收尾行）在 SQLite WAL 单写者下是否成立？事务内抛异常是否零提交？两个连接并发写时 busy_timeout 的实际行为与 BUSY 错误的错误类型、消息样本是什么（正式实现"报错与有限重试出口"的依据）？

**实验方法**：

1. 正常路径：一个 `@Transactional` 方法内插入一整轮多行（1 条 user + 2 条 assistant + 2 条 tool，共 5 行），提交后查询：行数=5；事务内分配的主键 id 连续（对照 TechnicalSolution.md - 9.2 SQLite 关系型数据"单写者下事务内行 id 连续"）。
2. 异常路径：事务内插入后抛 RuntimeException，回滚后查询确认零行落库（对照 agentos/CLAUDE.md 第 3 章"持久层抛异常即回滚并放弃该工作单元"）。
3. 并发组一（等待成功面）：两个裸 JDBC 连接（DriverManager 直连，隔离连接池语义；连接串与 D2 验证过的写法一致）交叠写同一库。连接 A 开写事务并保持，占用时长小于 busy_timeout 上限。事务体内只做写库与计时等待（短事务纪律，见 agentos/CLAUDE.md 第 3 章）。连接 B 同窗口发起写，记录 B 是等待后成功还是抛异常。
4. 并发组二（超时错误面）：同样交叠，但 A 的占用时长超过 busy_timeout=5000ms。记录 B 的异常类型与完整消息样本（SQLITE_BUSY 在 JDBC 层的面貌）。
5. 纪律注记：实验按 agentos/CLAUDE.md 第 3 章短事务纪律设计——事务体内禁止 LLM 调用、tool 执行等阻塞等待是正式实现红线，本实验只用计时等待模拟占用，不仿红线行为。

**通过判据**：

- 正常路径：行数=5、事务内 id 连续，两数实测留档；
- 异常路径：回滚后查询行数=0；
- 并发组一：记录实测结果（等待后成功，或异常——哪种都行，如实记录）；
- 并发组二：拿到 BUSY 错误的异常类型与消息原文样本；
- 四条证据各自落日志文件。

**优先级**：P0。轮原子提交是 TechnicalSolution.md - 4.3 关键设计点 (2) 的核心机制，"库中只含完整轮"的库内不变式全押在事务原语上。

### 2.4 D4：社区方言常规 JPA 面够用性（P0）

**验证问题**：社区方言（hibernate-community-dialects 6.6.53.Final 的 `org.hibernate.community.dialect.SQLiteDialect`）在常规 JPA 面上是否无坑：CRUD（增查改删）、BOOLEAN/BIGINT/TEXT/TIMESTAMP 字段映射、IDENTITY 主键、AUTOINCREMENT 关键字是否真落在建表 DDL 里、时间类型读写往返是否无损。该方言不在 Hibernate 官方 CI 测试矩阵内，常规面有没有坑只能实测。

**实验方法**：

1. 类型覆盖实体：一个实体含 Boolean、long、String、LocalDateTime 四类字段，主键 `@GeneratedValue(strategy = GenerationType.IDENTITY)`；实体按 agentos/CLAUDE.md 第 3 章"新表带 id、create_time、update_time"条款带时间列（顺带覆盖时间列映射，一举两得）。
2. CRUD 全链：Repository save → findById → 字段修改再查 → delete，每步用 AssertJ（Java 断言库，本仓编码规范指定的测试断言出口）断言。
3. DDL 回读：`PRAGMA table_info` 与 sqlite_master 查建表语句——主键列是否 `INTEGER ... AUTOINCREMENT`（AUTOINCREMENT 关键字必须真出现，`session_messages.id` 依赖此语义）；各字段列的声明类型逐列实录（SQLite 列类型是建议性的，实体声明的 BOOLEAN 实际落什么存储形态以实测为准）。
4. 往返校验：四类字段写入后读出逐字段比对；LocalDateTime 加两组边界样本（纳秒精度、跨时段时刻），记录实际存储形态（文本串还是整数）与往返是否无损。
5. 坑位登记：发现的坑逐条记录并三级归类——阻断（正式实现没法用）/ 有绕法（记录绕法）/ 无碍（仅记录差异）。

**通过判据**：

- CRUD 全链零错误、四类字段往返一致（逐字段比对结果留档）；
- DDL 实证 AUTOINCREMENT 关键字保留；
- 建表 DDL 与各字段存储形态实录落证据文件；
- 若有坑：坑清单 + 三级归类 + 绕法（若出现"阻断"级，写明影响哪些表与字段）。

**优先级**：P0。七张表（TechnicalSolution.md - 9.2 SQLite 关系型数据）全部押在这个方言的常规面上，这是第三周所有表的地基。

### 2.5 D5：synchronous=FULL 的 fsync 写放大量级（P1）

**验证问题**：synchronous=FULL 下，单次提交事务的真实耗时量级是多少？FULL 相对 NORMAL 的写放大倍数是多少？TechnicalSolution.md - 9.2 SQLite 关系型数据"每轮 2~4 次毫秒级 fsync，相对 60s 级 LLM 调用可忽略"的表述成立吗？（挂账五：2026-10-06 设计裁决"fsync 数字随 SQLite 落地实测校准"。）

**实验方法**：

1. 两组对照：同一实验程序跑两组——组 1 synchronous=FULL、组 2 synchronous=NORMAL。其余条件全同：同机、同库结构、WAL 开、每次提交事务写 1 行、连续 1000 次提交。
2. 计时：`System.nanoTime` 计时，记录每组总耗时与单次提交均值，经 SLF4J（Java 日志门面库，本仓编码规范指定的日志出口）打印留档。
3. 量级换算：按"一轮 = 1 次消息事务 + 每迭代 2 次审计事务（tool_invocations + llm_calls 各一行，逐次即时落库，见 TechnicalSolution.md - 4.3 关键设计点 (2)）"代入，算 10 次迭代一轮的提交开销合计，对照"60s 级 LLM 调用"量级。
4. 实验控制：必须用**文件库**（`:memory:` 内存库没有真实 fsync，测不出差别）；避开其他重 IO 进程干扰；机器空闲时跑。
5. 环境记录：执行日期、机型、磁盘类型写进结论。本机量级与目标部署环境（Linux 服务器）可能有差距，结论一律标注"本机量级实测"。

**通过判据**：

- 两组数字落证据文件：总耗时、单次提交均值（ms）、FULL/NORMAL 倍数；
- 结论明确回答：单次 FULL 提交均值是否 < 10ms（"毫秒级"的判据线）——成立则维持现行表述，不成立则触发回填改写（第 7 章结论回填联动（预登记）的联动 3）；
- 数字全部实测，禁估算。

**优先级**：P1。不阻塞第三周开工（功能正确性不受影响），影响的是性能表述的准确性与容量规划依据。

### 2.6 D6：版本组合整体回归（P1）

**验证问题**：hibernate-community-dialects 6.6.53.Final + sqlite-jdbc 3.49.1.0（两构件版本均由 Boot 3.5.16 的 spring-boot-dependencies BOM 托管：`hibernate.version`=6.6.53.Final 在 BOM 第 68 行、`sqlite-jdbc.version`=3.49.1.0 在第 203 行，2026-10-09 实测，出处见 1.3 版本组合基线（实测核验，2026-10-09））组合下，D1-D5 全链是否一次跑通？单点绿不等于组合绿，D6 是收口检查项，无独立实验。

**实验方法**：

1. 依赖坐标按 agentos/CLAUDE.md - 4 构建、依赖与 CLI（Maven 版本仲裁唯一等构建纪律章）：三方依赖不写版本号交 BOM 仲裁（sqlite-jdbc 不写版本；hibernate-community-dialects 用 `${hibernate.version}`——该属性由 Boot BOM 定义，与 agentos-storage 模块 pom 同写法）。
2. `mvn dependency:tree` 核查两构件的版本仲裁来源。
3. 全量测试：`mvn test` 一次跑通 D1-D5 全部测试。

**通过判据**：

- `mvn dependency:tree` 输出显示 `org.xerial:sqlite-jdbc:jar:3.49.1.0` 与 `org.hibernate.orm:hibernate-community-dialects:jar:6.6.53.Final` 均由 BOM 仲裁、无第二版本；
- `mvn test` 的 Tests run 数字留档，Failures=0、Errors=0；2026-10-10 用户裁决修订：Failures ≤ 2 且仅限 D4 两坑坐实断言、Errors=0。两红合理的理由——D4 对两坑各写的是「正确行为」断言（建表 DDL 应含 AUTOINCREMENT、LocalDateTime 纳秒应往返无损），社区方言做不到，测试红就是坑的实测证据本身：按 R6 纪律明知有坑仍不降级判据、让坑以测试红留证，其余 15 例（D1-D3、D5 全部与 D4 机制面）全绿。与原判据不矛盾的理由——本条「Failures=0」起草时针对的是探针工程自身的实现缺陷（回归质量），D4 两红是测量结论、不是实现缺陷：被测对象（版本组合仲裁与 CRUD 机制）本身合格，红的只是方言行为与期望的差距，两者正交；判据先于执行写成全绿、未预见 D4 会探出坑，故本次属判据适用范围收窄、不是达标口径放宽。实测 17 run / 2 Failures / 0 Errors（处置见 README 决议表 D4/D6 行）；
- 结论写入 README 的"版本组合"决议行。

**优先级**：P1（收口性质，依赖 D1-D5 先完成）。
