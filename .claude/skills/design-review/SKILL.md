# 设计文档评审（Design Review）

## 目标

对一组相互关联的设计文档做跨文档、多维度的结构化评审，产出一份**评审报告**。报告要让未参与评审的人也能理解每个问题的来龙去脉，并附措施选项与建议，供项目方拍板后另行修复。

**边界（重要）**：
- 本 skill **严格只读**——不修改任何被评审文档，不生成修复 commit
- 修复文档是评审完成后的独立后续工作，不在本 skill 范围内
- 遇到需要项目方拍板的决策点（如架构取舍、范围收缩），**停下来用 AskUserQuestion 问用户**，不要自行替用户做主

---

## 评审人画像（谁适合参与评审）

一次高质量设计评审需要以下视角，可由一人或多人覆盖。skill 运行时应在报告开头输出简化版建议。

**必备能力（缺一评审质量会显著下降）**：

| 角色 | 能力要求 | 覆盖的评审维度 |
|------|---------|--------------|
| **架构视角** | 理解系统分层、模块划分、接口抽象；能判断"接口先行 vs 直接实现"这类取舍的合理性 | 接口边界、模块归属、阶段归属边界 |
| **实施视角** | 有从设计文档到代码的落地经验；能预判"实施者（人或 AI agent）读到这里会理解成什么、会写错什么" | 实施约束与防偏、工具链/工作流准确性 |
| **产品/需求视角** | 理解验收标准的可判定性；能发现"写得模糊导致验收时扯皮"的条目 | 验收标准精确性、数量与枚举完整性 |
| **文档工程视角** | 细致、擅长跨文档比对；能系统性地 grep 同一概念在所有文档中的表述 | 术语一致性、跨文档交叉引用、图文一致性 |

**不适合单独承担评审的人**：
- 只写过其中一份文档的人单独评审（会自我确认，跨文档盲区大）
- 对技术栈不熟悉的人评审技术方案细节（无法判断接口边界合理性）

## 评审维度体系（核心关注点）

按维度组织检查，不按文档组织。**默认全部 14 个维度都跑**；用户通过 `--focus` 指定时只跑指定维度。

每个维度附严重程度判定标准：
- **高**：影响实施正确性——实施者会写错方向的
- **中**：影响实施计划——任务拆分、时序、范围会错的
- **低**：一致性修缮——不影响实质但影响文档质量的

### 1. 术语一致性
同一概念在所有文档、所有位置（含表格、术语表、总结章节）是否同名称、同定义、同粒度。重点盯**演进过的术语**（含义发生过调整的概念最容易漂移）。
检查法：提取核心术语清单 → 在全部文档中逐一 grep → 比对每处表述。
典型问题：同一机制一处叫"极简版"另一处叫"默认档"；方法名 enforce/check 混用。严重程度：中。

### 2. 接口边界与职责划分
模块/服务间职责是否清晰分离、无重叠、无歧义。重点：一个组件的职责描述是否在多处矛盾；两个相近概念（如校验 vs 执行、入站 vs 出站）是否被混同。
典型问题：MemoryService 到底注入会话历史还是只注入长期记忆，两处描述不同。严重程度：**高**（直接决定代码实现方向）。

### 3. 数据模型完整性
功能设计引用的实体/表/字段是否都有定义；字段级是否逐一对齐（需求文档定义 vs 技术方案建表）。反向检查：新加的功能有没有对应的数据落点。
典型问题：新增了管理功能但数据模型章节没有对应表；配置结构加了字段但派生映射清单没同步。严重程度：高（缺失）/中（不对齐）。

### 4. 实施约束与防偏
站在实施者（尤其是 AI agent）角度预判易错点：文档是否在易错处有显式约束、警示、检查项。重点：框架的"自动化便利"与设计的"显式控制"冲突处（实施者会顺手用便利路径）。
典型问题：超时被硬编码、自动重试被默认启用、无接口的单档实现。严重程度：**高**。

### 5. 跨文档交叉引用
章节号引用是否指向正确内容；引用方式是否稳健（章节号易失效，描述性引用更稳）。检查法：逐条提取"见 X 章"类引用 → 跳转验证。
严重程度：低（指向错误为中）。

### 6. 阶段归属边界（核心 vs 扩展）
每个功能/能力的阶段归属在所有文档中是否一致；"核心阶段不做"清单是否对齐。重点：范围收缩决策后是否有残留的旧范围表述。
典型问题：某能力一处说"核心阶段交付三档"，另一处已收缩为"接口+默认档"。严重程度：高。

### 7. 模块归属一致性
每个组件在哪个模块的表述是否与权威定义（通常是架构章节的模块清单）一致。实施拆分文档（user story / 任务清单）里列的模块尤其容易漂。
典型问题：ConfigLoader 一处归 core、一处归 cli。严重程度：中。

### 8. 数量与枚举完整性
文档中的所有计数（端点数、Controller 数、目录数、工具数、命令数）与逐项枚举是否一致、是否与实际列表长度相符。检查法：找到每个"N 个 XX"声明 → 数实际的枚举列表。
典型问题：加了功能后"6 个 Controller"没改成 8。严重程度：中。

### 9. 验收标准精确性
每条验收标准是否可判定（能明确说通过/不通过）、可复现。重点区分"最终完整验收"与"阶段性部分验收"的表述；模糊词（完整、全部、自动）是否有精确语义。
典型问题："查到完整对话记录" vs 实际机制只保留"最近对话记录"。严重程度：高。

### 10. 图文一致性
架构图/流程图（SVG、mermaid 等）与文字描述是否对齐。检查法：对每个已改动的文字概念，检查对应图中的标签、模块框、箭头是否同步。
典型问题：文字已把两个模块合并，图里还是两个框。严重程度：低。

### 11. 风险与遗漏
主动识别文档未覆盖的风险场景（测试被省略、成本失控、工程量超预算、并发/失败/超时等边界路径），并检查是否有对策。
严重程度：中。

### 12. 工具链/工作流准确性
文档描述的工具使用方式（命令、流程、artifacts 结构）是否符合该工具的实际用法。适用条件：文档涉及具体工具链（如 spec-kit、CI、构建工具）。需查工具最新文档验证，不凭记忆。
严重程度：中。

### 13. 时间线与里程碑一致性
里程碑/周计划的描述与各阶段拆解的内容是否对齐；每个中间里程碑是否有可判定的完成标准。
严重程度：低（里程碑内容缺失为中）。

### 14. 可维护性
重复信息的 source of truth 是否声明；引用是否易失效；文档间职责边界是否合理（详细定义放错了文档层级）。
严重程度：低。

## 执行流程

### 第 1 步：确定评审范围（必做，信息不足时问用户）

1. 读取 `$ARGUMENTS`。若有明确的文档路径列表，直接使用。
2. 若参数为空或模糊：**先扫描项目找候选文档**（常见位置：`docs/`、`.specify/`），然后用 AskUserQuestion 问用户：
   - 要评审哪些文档？
   - 每份文档的定位是什么（What / How / How to execute / 背景参考）？
   - 是否只聚焦部分维度？
3. 默认模板（用户不特别说明时套用三件套定位）：
   - 需求文档（What，回答"做什么"）
   - 技术方案（How，回答"怎么做"，是实施的直接依据、上下游契约的权威定义）
   - 实施指南（How to execute，回答"怎么组织实施"）
   - 若文档集与默认模板不同，按用户声明的定位构建依赖关系。

### 第 2 步：建立文档地图

通读各文档目录结构，记录：
- 每份文档的章节清单
- 文档间的引用关系（谁引用谁、引用哪些章节）
- 确定每类信息的 source of truth（如：数据模型详细定义以技术方案为准）

### 第 3 步：逐维度检查

按上面 14 个维度依次检查（`--focus` 时只查指定的）。每个维度：
1. 用该维度的检查法系统扫描（grep 术语、数枚举、跳转引用…），不靠浏览印象
2. 发现问题时记录：位置（文档+章节）、原文表述、冲突/缺失的对方位置
3. 按"发现依据→问题描述→后果"整理，**不修改文档**

约束：聚焦高信号发现，总量控制在 50 条以内；同类小问题（如同一术语在 10 处不一致）合并为一条，位置列表合并给出。

### 第 4 步：整理措施选项与联动组

对每个问题：
- 给出至少一个推荐措施；存在多种合理方案时列选项 A（推荐）/B（备选），各附理由、影响、风险
- 涉及架构/范围取舍的选项**不替用户选**——汇总到"需要架构决策的问题"表，或在报告中明确标注"需项目方拍板"
- 跨文档联动的问题归入联动组，给出修改顺序建议与原子提交组建议

### 第 5 步：产出评审报告

写入 `draft/review/review-report-<YYYY-MM-DD>.md`（`draft/review/` 不存在时先创建）。报告结构：

```
# {项目} 设计文档评审报告
> 评审时间 / 评审范围 / 评审维度 / 报告依据

## 建议评审人背景          ← 简化版画像，3-5 行，按本次文档集特点定制
## 评审概览                ← 指标表 + 按维度的问题分布表
## 发现的问题              ← 每条一个条目，模板见下
## 跨文档联动修改组        ← 联动主题、关联问题 ID、修改顺序建议
## 需要架构决策的问题      ← 决策点、选项、推荐与理由（标注"需拍板"）
## 评审总结                ← 整体评价 + Top 3 优先项 + 建议后续动作 checklist
```

**问题条目模板**（每条必须含全部字段，让未参与评审的人能独立理解）：

```markdown
### [编号] 问题标题
**维度**：{维度名}
**严重程度**：高 / 中 / 低
**涉及文档**：{文档+章节位置列表}

**发现依据**：{推理过程——A 处写 X，B 处写 Y，为何矛盾/缺失}

**问题描述**：{原文怎么写的、为什么有问题、不修正会误导实施者做什么}

**推荐措施**：
**选项 A（推荐）**：{描述}
  - 理由 / 影响 / 风险
**选项 B（备选）**：{描述，无可选项时省略}

**实施建议**：
  - 修改顺序：{多文档联动时的先后}
  - 原子提交组：{哪些必须一起提交}
  - 验证方式：{改完后如何验证，如 grep 旧术语确认无残留}
```

### 第 6 步：汇报

在对话中输出报告摘要（概览表 + Top 3 + 决策点清单）并给出报告文件路径。**明确提醒用户**：报告中的措施是建议，修复文档是后续独立工作；有"需拍板"项时应先决策再修复。

## 运行原则

- **只读**：全程不修改被评审文档；报告只写到 `draft/`
- **按维度组织，不按文档组织**：同一概念的问题跨文档合并为一条
- **证据优先**：每个问题必须引用具体位置和原文，不写"某处大概说了"
- **不替用户拍板**：架构取舍类决策明确标注并询问
- **可复现**：给出的验证方式应能机械化执行（grep、数数、跳转）
- **零问题也如实报告**：输出概览统计与"未发现问题"的维度清单
