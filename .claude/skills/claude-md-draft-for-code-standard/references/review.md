# 三路对抗评审操作手册（claude-md-draft-for-code-standard 第⑧步）

> 本文件职责：定义第⑧步三路对抗评审的执行规格——评审组织方式、五项恒定检查（含回潜 grep 操作步骤与自举合规三值判定）、发现分级与处置闭环、评审产物落盘契约。
> 上游：skill-design.md——裁剪依据见 §4 裁剪总表（⑧⑨ 恒定）与步骤表 ⑧行 / ⑨行；评审预算见 §4 步骤表 ⑧行 + 附录 C；人类可读性检查项口径见本文件 §3.3（三路评审机制的素材甄别见附录 F「带走」清单）。
> 下游：第⑨步「修订落盘+状态说明」消费 §5 的评审产物与「修订完成」标记行；skill 打包后本文件作为 references/ 底稿，供第⑧步评审 agent 读取。

## 1. 定位与输入产出

- 第⑧步是恒定步、最后一道闸，fail-fast：评审未通过不得进入第⑨步落盘。
- 输入（必须齐备后才可开评）：
  - ⑦初稿：五段预算结构——文件头（效力锚）/ 固化骨架 / 入选正文 / 提示区 / 块级 HTML 豁免注记（状态块全部字段整体置本段注释区、不计行数）；≤200 行（口径 = 注入后对 agent 可见行数，即全文减 HTML 注释行）。
  - ⑥否决清单：`draft/final-selection.md`，含死因枚举 + 特征 token 集。死因枚举四值：因果链自相矛盾 / 触发面为空 / 覆盖被占满 / 机制含混。否决清单是回潜 grep 的唯一数据源——清单未落盘则该检查不可执行，先回③/⑥补落盘再评审。
- 产出：`draft/review.md`，内容为评审发现 + 采纳/驳回处置 + 「修订完成」标记行。标记行由第⑨步追加，见 §5。
- 评审边界：评审对象是⑦初稿与⑥否决清单的执行质量，不是重开③④⑥的评分与终选裁决。对已否决条目的翻案只有 §3.4 回潜 grep 的「显式改判」出口。
- 引用纪律：评审发现涉及判例内容时，必须回查 `code-style-guidance/` 落盘原文，禁止凭记忆引用。provenance 三值 crawled / user-provided / pre-packaged 同池，均以落盘原件为准。回查不依赖 URL 可达性——验证失败≠失效，fetch_failed 判例仍以已落盘原文为准。

## 2. 评审组织：独立上下文与预算档位

- 独立上下文，禁起草者自评：执行评审的 agent 不得与第⑦步起草共用上下文。
- 预算两档，二选一：
  - 默认档：3 个独立 agent。视角隔离优先——must_fix 级发现「禁内联事件措辞封死交互组件」即由独立视角抓出。
  - 降级档：单 agent 三轮换视角。两态切换规则：交互可得（用户在线可应答）时，仅限预算敏感的小项目且经用户显式确认后切换；交互不可得（无人值守运行 / 上游限流 429 / agent 超时）时，允许默认降级，但必须同时满足：①产物内声明降级及原因（review.md §1）；②汇报显著标注「评审为降级档」；③覆盖面不裁剪（见下条）。
- 覆盖面不随档位裁剪：⑧为恒定步，五项恒定检查在两档下都必须逐项执行。本文件不硬性规定检查项到 agent/轮次的分配，只规定合计覆盖必须完整，且每条发现必须标注所属检查项。

## 3. 五项恒定检查

> 第⑧步名为「三路对抗评审」，实际执行五项恒定检查：前三项对应三路视角（通用性泄漏 / AI 可执行性 / 人类可读性）；回潜 grep 与自举合规为另两项。

### 3.1 通用性泄漏

按双向检查，两个方向都算失败：

- 泄漏方向：站点取值、项目品牌名/站名、内部路径、行号、日期等本站特定信息直接写死进对 agent 可见正文。对应草稿红线 2：正文无行号、无日期、无项目品牌名/站名/内部路径；技术栈名是必要标识，须按官方拼写。
- 空洞化方向：为规避泄漏删光站点内容，写成谁都能用的正确的废话。这是通用化的禁用歪路之一。
- 合法形态判据：站点内容照写，写成条件式 + 站点参数清单（编号键值对表）。标为「站点特定」的条款必须已落参数清单键。迁移性三值：通用 / 同类栈 / 站点特定。
- 检查产出：逐条列出泄漏项（定位 + 违反的红线条号）与空洞化项（定位 + 缺失的判据/参数），全部按 §4 分级处置。

### 3.2 AI 可执行性

两个子检查，逐条执行：

- 子检查一，执行者歧义（字面执行审查）：对每条禁令/指令做字面执行推演，并**逐条构造反例场景留痕**——每条禁令至少给出「一个按字面执行会被误伤的具体合法场景」（引用真实文件或构造示例）；构造未果的逐条显式记「构造未果」，禁止以笼统「未发现问题」代替构造。按字面执行会封死合法场景的，必须收窄措辞。判例：初稿「模板禁内联 style 与行内事件」——「行内事件」即 @click 内联处理器，字面执行封死一切交互组件；终稿收窄为只禁内联样式属性。
- 子检查一配套，**强度-证据对齐核验**：对照源证据（判例落盘原文 / 盘点证据 / 指南原文）逐条核对条款的模态强度与限定范围，任一命中即计 must_fix：源证据为建议性措辞而条款写成绝对禁令；源证据的场景限定在条款中丢失；单版本观察被外推为跨版本断言。规则全文见 scoring.md §1.2「转写强度对齐」。判例：判例原文 "should most likely be avoided"（且原文自认性能优先级低）被写成「禁通配符关键选择器」。
- 子检查二，条款自足性：单条条款不依赖会话上下文或外部说明，即可判定「何时适用、如何执行、违反判据是什么」。含不可判表述即计发现。对应草稿红线 7：全文无不可判表述。
- 失败模式登记表对应条目：禁令字面执行封死合法场景 → 字面执行审查（本子检查）。
- 分工边界：本检查评「条款能否被 agent 无歧义执行」（写法层）；「AI 会不会犯这条」（选材层）属③必维 AI 犯错要件，评审不重评、不在评审中复活选材判断。

### 3.3 人类可读性

逐条检查（三路评审属素材甄别「带走」项，见 skill-design.md 附录 F；检查项口径以本节为准）：

- bullet 密度：连续长 bullet 列表导致扫读失效的段落。
- 粗体导语：长条款缺粗体导语，导致关键约束不可快扫。
- 术语首现：官方术语首现未给原文括注（语言约定口径）。
- 检查产出：逐项定位 + 修改建议，按 §4 分级处置；不影响执行正确性的仅记 suggest。

### 3.4 回潜 grep

检查定义：终选已否决的条目又悄悄写回初稿，即回潜。用确定性检索防主观遗漏。判例：已否决的「Be consistent」与「config 新增键门槛」被评审抓出写回。

操作步骤：

1. 提取 token：读取 `draft/final-selection.md` 否决清单，逐条采用其已落盘的「特征 token 集」——否决项条款主题词、机制名、配置键等可检索词。个别否决项未落盘特征 token 时，以该条死因枚举中的判别词补足，并把补足结果记入 `draft/review.md`；不得凭记忆另造，不得跳过该条。
2. 逐一检索：对每个 token 在⑦初稿全文逐一检索。全文含 HTML 注释行，白名单判定在下一步做。记录每个 token 的命中处（行号）与命中数。
3. 白名单判定：唯一白名单 = 块级 HTML 注释区。
   - 命中行属于块级 HTML 注释区 → 不计回潜。理由：草稿红线 9 规定人类专用元信息——勿再加清单 / 参数清单 / 复用方法 / 元规范出处 / 状态块 / 遗留规范对照——只进块级 HTML 注释；勿再加清单合法记录否决理由，其特征 token 出现在该区属预期。
   - 命中行在 HTML 注释区之外（即注入后对 agent 可见正文）→ 计回潜。
4. 命中处置：只有两个合法出口，逐命中二选一。
   - 出口 a（删除）：从正文删除该回潜内容。
   - 出口 b（显式改判）：推翻既有否决——显式改判必须引用既有死因并写明翻转理由。
   - 无第三出口：保持原样、仅在汇报中口头说明、静默忽略均禁止。
5. 落盘检索记录：逐 token 记入 `draft/review.md`——token / 命中处 / 白名单判定 / 处置与出口。零命中也逐 token 记「未命中」。处置记录强制落盘。

### 3.5 自举合规（三值判定）

检查定义：草稿必须遵守它自己立的规则，逐条三值判定。判例：初稿自己写了小写 css/yaml，被自己的专名大小写条款抓出。

判定规程：

1. 列规则清单：提取草稿自身立出的全部规则——入选正文的纪律条款 + 提示区自描述演进纪律，逐条编号，不漏条。
2. 逐条对草稿全文自检：该条款所规定的行为，草稿自身文本是否遵守。判定三值：
   - `合规`：草稿全文均符合该条款，且能指出至少一处自检过的对应文本面。
   - `违反`：草稿自身存在违反该条款的文本，一律计 must_fix。
   - `不适用`：该条款在本次草稿内无可自检的文本面（如草稿未含命令则命令红线无检验面）。必须写明不适用理由，禁止用不适用掩盖可检未检。
3. 自检面覆盖九条草稿红线对应项。例：≤200 行按「注入后对 agent 可见行数 = 全文减 HTML 注释行」口径复核⑦记录的 200/估算/实况三数；提示区须已写入自描述演进纪律。九条草稿红线清单见同目录 `template.md` 第 3 节「起草红线九条」；打包后为 `references/template.md`。
4. 判定表落盘 `draft/review.md`，字段：规则编号 / 判定值 / 依据或理由。见 §5。

## 4. 发现分级与处置闭环

- 发现分两级：`must_fix` / `suggest`。
- must_fix：阻断落盘。全部 must_fix 修复完成后才允许第⑨步落盘（fail-fast）。must_fix 修复属默认不问项：自动修订，不询问用户（用户交互点矩阵口径）。
- suggest：逐条显式采纳或驳回，禁止静默忽略；驳回必须写明理由。
- 全部发现（含驳回项）的处置结果落盘 `draft/review.md`，形成可指认的闭环记录。每条发现必须能查到「发现 → 分级 → 处置（采纳/驳回/修复）」的完整链。
- 失败模式登记表对应条目：评审产物未落盘 → 处置记录强制落盘（见 §7）。

## 5. 评审产物契约（`draft/review.md`）

`draft/review.md` 必须包含以下五部分，缺一即视为产物未落盘：

1. 评审组织记录：预算档位（3 agent / 单 agent 三轮）与各路（轮）覆盖的检查项。
2. 评审发现清单：逐条标注四项——所属检查项（§3.1-§3.5 之一）；位置（文件 + 行号/条款定位）；问题描述；分级（must_fix/suggest）。
3. 处置记录：逐条采纳/驳回 + 理由；回潜 grep 检索记录（§3.4 步骤 5）；自举合规判定表（§3.5）。
4. 修订结果：must_fix 逐条修复情况。
5. 「修订完成」标记行：由第⑨步在 must_fix 全部修复落盘后追加于文件末尾。该标记是 ⑧→⑨完成记录，不承担续跑判定。

## 6. 第⑨步收尾与汇报清单

> 第⑧步评审通过（must_fix 清零）后进入第⑨步「修订落盘+状态说明」（恒定步）：输入 ⑧记录 + ⑦初稿，产出 终稿 + 汇报。本节只约定与 `draft/review.md` 衔接的收尾契约；评审侧职责止于把 §5 五部分落齐。

- 落盘前置（fail-fast，与 §4 同口径）：must_fix 全部修复完成后才允许第⑨步落盘；就地修订⑦初稿，不另立文件。
- **落盘前终局机检（fail-fast）**：⑨修订完成后、追加「修订完成」标记前，执行以下五项机械检查。命中一律按 must_fix 处理（机检项均为客观判据，无 suggest 档）；每条命中二选一——修复（改终稿）或显式改判（核实为检查误报时，记录误报理由并修正检查方法），禁止静默保留；修复后重跑直至五项全过，方可在本文件末尾追加「修订完成」标记。机检记录（检查项 / 命中 / 处置）落 `draft/review.md`：
  1. **指针闭合**：正文中全部「见 S-xx / 见 P-xx / 见 C-xx」及「先例在册」类指代，目标必须真实存在（逐一对照待沉淀节编号、参数清单键、候选台账）。
  2. **条款冲突扫描**：引用同一配置键、同一文件或同一机制的话题簇内，条款指令方向必须相容；结论相反且无显式例外声明 = 命中。
  3. **TODO 键名逐字相等**：提取正文全部 `TODO(参数名)`，与参数清单键名逐一比对，必须逐字一致；近义不同名 = 命中。
  4. **PENDING 字段格式**：参数清单中状态为 PENDING 的行，「当前值」列必须留空，「影响条款」列必须为条款编号或「无」。
  5. **行数三数复核**：按唯一机械口径重算可见行数 = 全文行数（`wc -l`）− 以 `<!--` 开头的行数（`grep -c '^<!--'`），与状态块「行数三数」比对，不一致以实测回填。
- 状态说明落稿：状态说明三要素（来源组合与证据等级 / 未决参数 / 待沉淀节指针）+ 变更记录写入终稿状态块——整体置于第 5 段块级 HTML 注释区、不计行数（template.md 第 4 节）。
- 遗留规范对照（⑨契约要点）：时机 = 终稿落盘后执行；⑦ 及之前任何步骤禁止读落点既有 CLAUDE.md（独立性硬保证——既有 CLAUDE.md 仅作⑨事后对照，非输入源，仍一字不改）。对照三值：一致（仅计数，禁止逐条列出）/ 差别（一方有一方无：新增=新有旧无、未采纳=旧有新无）/ 冲突（同类话题结论相反）；**差别与冲突必须逐条全列**（条款定位 + 两侧各一句话摘要），禁止「列 N 项代表」缩水。最小产物 = 逐话题两侧结论对照表（话题 / 新稿结论 / 旧稿结论 / 三值判定），以话题为扫描单位逐一判定，防漏报。落点 = 终稿末尾块级 HTML 注释区新增「遗留规范对照」子块（人类可读、不计入 200 行口径、不进 agent 上下文）。
- **注入污染披露（⑨强制）**：落点存在既有 CLAUDE.md 且运行中读取过落点目录内文件的，视为发生过 harness 级自动注入（读目录内文件时既有文件被注入上下文，文字纪律无法阻断）。此时状态块必须记「对照受注入污染风险：产出可能与既有文件存在无出处的同源措辞」；「遗留规范对照」子块与汇报中的对照结论必须标注「仅供人工参考，不作为合并唯一依据」，并建议对冲突判定做人工独立复核。
- 汇报必列六项，缺一即汇报不完整：
  1. 终稿路径。
  2. 三行数：红线 200 / 估算 / 实况，即⑦记录三数。
  3. 来源组合与证据等级。
  4. 未决参数。
  5. Action 移交清单：⑤工单摘要全列，供用户裁决是否修复（工单定义见 skill-design.md §4 ⑤行，工单模板见同目录 template.md 第 4.4 节）。
  6. 遗留规范对照摘要：差别 / 冲突计数 + 要点（一致项仅计数；全文见终稿 HTML 注释区「遗留规范对照」子块）。
- 「修订完成」标记时机：must_fix 全部修复落盘后，由第⑨步追加于 `draft/review.md` 文件末尾。完成记录口径与 §5 第 5 项一致，本节不另立新规。

## 7. 评审相关失败模式对照（执行前自检）

| 失败模式 | 预防规则 | 本文件落点 |
|---|---|---|
| 否决项回潜 | 回潜 grep | §3.4（数据源=⑥否决清单特征 token 集，缺清单先回③/⑥补落盘） |
| 禁令字面执行封死合法场景 | 字面执行审查 | §3.2 子检查一 |
| 评审产物未落盘 | 处置记录强制落盘 | §4、§5 |
| 起草者自评（视角不隔离） | 独立上下文 + 默认 3 agent | §2 |
